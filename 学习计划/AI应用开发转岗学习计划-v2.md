# AI 应用开发 / Agent 开发 转岗学习计划 v2（2026-11 修订）

> 适用对象：在职前端开发者（JS/React 熟练；Node.js 后端与数据库已补到第 10 周）
> 修订原因：2026-08 的 v1 按 TypeScript 单栈设计。2026-11 市场核查发现三件事变了——**Python/FastAPI 成了硬门槛、MCP 已标准化、评测闭环成了面试分水岭**。证据与逐项对照见 [市场对齐检查-2026-11](./市场对齐检查-2026-11.md)。
> 变化：36 周 → 32 周（在职按 32–36 周弹性执行，见第十五节）；第 13 周起 Python 为主线；新增 MCP、评测、上下文工程、生产化；**第 26 周开始投递**。
> 不变：工程基础、PostgreSQL、手写 ReAct、项目驱动、生产级标准。

## 一、目标和定位

- **目标岗位**：AI 应用开发 / 大模型应用开发 / Agent 开发（国内社招为主）
- **差异化**：前端出身 + 能独立交付 RAG/Agent 服务 + 生产级 ChatUI + 拿得出评测数据
- **不冒充算法工程师**：不训练模型，讲清"集成、编排、评测、成本、稳定"这五件事
- **语言策略**：Python 写服务端 AI 逻辑；TypeScript 写前端与 ChatUI；Node.js 作为已掌握的第二栈，不退场
- **一句话标准**：能对着一条真实 JD，把自己的项目从"方案 → 开发 → 部署 → 评测 → 迭代"讲完整

## 四、阶段三：Python + LLM 应用（第 13–20 周）

**这一阶段的定位**：把已经会的后端能力（HTTP、分层、SQL、事务、鉴权）平移到 Python，再往上叠 LLM / RAG / 评测 / MCP。**不学数据分析、爬虫、机器学习**，只学"服务端 AI 工程"用到的那部分。

### 第 13 周：Python 桥接（一）——语言与工具链

**目标**：把"会 TS"迁移成"能读能写 Python 服务代码"，不学新业务。

- [ ] 语法对照：类型注解、`dataclass` / Pydantic、`async/await`、生成器与 `AsyncIterator`、异常体系
- [ ] 工具链：`uv`（依赖 + 虚拟环境）、`ruff`（lint + format）、`pytest`、`mypy`（可选）
- [ ] 用 Python 重写第 6 周的 tasks service + repository（先不接 HTTP）
- [ ] 写 5 个 pytest 用例：成功、参数非法、找不到、越权、边界

**产出**：`代码练习/阶段三-AI应用/week13/`，`pytest` 全绿；补一份 `生产级代码规范-Python版.md`（分层 / Pydantic / 错误处理 / 日志 / ruff 规则）。
**面试点**：Python 的 async 与 Node 事件循环的差异；Pydantic 与 zod 的取舍。

### 第 14 周：Python 桥接（二）——FastAPI 重写待办 API

**目标**：同样的接口，用 FastAPI 写一遍，行为和 TS 版一致。

- [ ] FastAPI：路由、依赖注入（`Depends`）、Pydantic 请求/响应模型、异常处理器、中间件、`lifespan`
- [ ] `StreamingResponse` 做 SSE：`text/event-stream`、分段 `data:`、断连处理
- [ ] SQLAlchemy async + asyncpg：对照 Prisma 的 model / 关系 / 事务
- [ ] `pytest` + `httpx.AsyncClient` 冒烟测试；`ruff` + `mypy` 进 CI

**产出**：FastAPI 版 auth + tasks API + 一个 SSE 流接口；命令一条起服务，测试全绿。
**面试点**：FastAPI 的依赖注入比 Express 中间件好在哪；SSE 为什么不用 WebSocket。

### 第 15 周：LLM API、流式与结构化输出

- [ ] OpenAI 兼容接口（DeepSeek / Qwen / GLM 任选）：`chat/completions`、`stream`、错误码、限流
- [ ] 客户端封装：超时、指数退避重试、`AbortController` 式取消、token 统计
- [ ] 流式：后端转发 SSE，前端 `fetch` + `ReadableStream` 手动解析（处理半包）
- [ ] 结构化输出：Pydantic / JSON Schema，校验失败自动重试一次
- [ ] 参数实践：temperature、max_tokens、stop、seed

**产出**：命令行多轮聊天 + `/chat/stream` 接口 + 一个"稳定返回 JSON"的抽取接口（连续 20 次不合法率 < 5%，把数字记下来）。
**面试点**：流式半包怎么处理；结构化输出有哪几种实现路径。

### 第 16 周：Prompt 工程 + 上下文工程

- [ ] 系统提示 / 任务模板 / 用户输入的分层；XML 分隔符优于 Markdown
- [ ] Few-shot、CoT、ReAct 的区别与适用场景
- [ ] **上下文工程**：token 预算分配、历史摘要压缩、工具输出截断、记忆分层（工作 / 短期 / 长期）
- [ ] 上下文超长时的裁剪策略；"Lost in the Middle" 的影响
- [ ] Prompt 版本化：像代码一样 review / 回滚

**产出**：一个可切换上下文策略的对话服务 + 一张对比表（同 10 个问题，不同策略的 token / 质量 / 延迟）。
**面试点**：上下文爆炸怎么办；为什么"塞更多上下文"不等于"效果更好"。

### 第 17 周：RAG 索引侧

- [ ] 文档解析：PDF / Markdown / 网页（PyMuPDF、docling 或 MinerU），表格与扫描件的坑
- [ ] 分块：固定长度 + 重叠、递归分割、父子分块、按结构切
- [ ] Embedding：`bge-m3` 或 DeepSeek embedding；查询与文档的前缀差异
- [ ] 入库：pgvector 建表、批量写入、元数据（来源 / 页码 / 权限）、增量更新
- [ ] 索引：HNSW 参数（`m`、`ef_construction`）与召回率的关系

**产出**：`ingest` 命令行：给一个目录，输出 chunk 数、向量数、耗时；重复执行幂等。
**面试点**：块太大/太小分别什么问题；增量索引怎么做。

### 第 18 周：RAG 检索侧

- [ ] 混合检索：向量 + BM25，RRF 融合（能手写公式）
- [ ] 重排：粗召回 top50 → `bge-reranker` 精排 top5；为什么不用 embedding 直接精排
- [ ] 查询改写：HyDE、多查询扩展、子问题分解（至少实现一种）
- [ ] 引用溯源：答案带 `[1][2]`，能点回原文
- [ ] 拒答：检索不到 / 分数过低时明确说"不知道"，不自由发挥

**产出**：`/ask` 接口：问题 → 检索 → 重排 → 生成 → 引用；准备 10 个"应该拒答"的问题验证。
**面试点**：混合检索怎么融合；幻觉怎么治理。

### 第 19 周：评测周（本周决定你是"Demo 工程师"还是"生产工程师"）

- [ ] 建评测集：从文档里出 30–50 条（问题 + 标准答案 + 出处），覆盖单跳 / 多跳 / 拒答
- [ ] 指标：Recall@5、MRR、忠实度（Faithfulness）、答案相关性、P95 延迟、单次成本
- [ ] 工具：Ragas 跑 RAG 指标；Langfuse 接 trace（每次调用的 prompt / 检索片段 / token / 延迟）
- [ ] 做一次优化（改分块或加重排），跑前后对比，把提升写进报告

**产出**：`eval/` 目录 + 评测报告（基线 vs 优化后）+ Langfuse 截图；报告里每个数字都能复现。
**面试点**：Recall@K 怎么算；怎么证明你的优化有效。

### 第 20 周：MCP、Skills 与工具调用

- [ ] MCP 三大原语：Tools / Resources / Prompts；stdio 与 Streamable HTTP 传输
- [ ] 用 FastMCP 写一个 Server：2–3 个工具（查数据库、搜索、读文件）
- [ ] 客户端接入：Claude Desktop / Cursor，或自己的 Agent 当 client
- [ ] 安全：工具权限最小化（只读优先）、参数校验、prompt injection 防护、审计日志
- [ ] Skills：`SKILL.md` 的组织方式，与 MCP 的分工（能力封装 vs 工具接入）
- [ ] 了解 A2A：Agent ↔ Agent 的边界，什么时候需要

**产出**：一个可被外部客户端调用的 MCP Server + 演示录屏 + 一页安全说明。
**面试点**：MCP 解决什么问题；MCP 和 Function Calling 是什么关系。

## 七、每周节奏与收尾硬标准

| 时间 | 安排 |
|---|---|
| 周一至周四 19:30–21:00 | 学新概念 + 跟练小例子 |
| 周五 | 休息 / 补账，不排新内容 |
| 周六上午 | 整块时间做产出 |
| 周日 | 3 小时项目 + 1 小时复盘 |

**每周收尾硬标准（缺一不算过周）**：

1. **能跑通**：一条命令复现，不依赖"上次那个终端"
2. **已提交**：至少 1 次 commit，message 写清范围（`feat(rag): ...`）
3. **有笔记**：概念 + 踩坑 + 面试问答，三段式
4. **有演示**：截图 / 录屏 / `curl` 输出，放进 README
5. **WIP ≤ 2**：未收尾项不超过 2 个；超了先清账，再学新的
6. **周日 30 分钟复盘**：本周产出 / 欠账 / 下周计划，写进快照

**每周固定小习惯（不占主线）**：2 道 LeetCode（中等）、1 篇官方文档或 release note、1 次 commit。

## 八、贯穿要求：评测与可观测（AI 项目的"有没有做过"分界线）

每个 AI 项目都必须有：

- **评测集**：≥ 30 条，覆盖正常 / 边界 / 应拒答

- **README 数字**：优化前 → 优化后，写清楚改了什么

没有数字的项目，在面试里等于"跟着教程做过"。

## 十、并行线：把现公司变成"生产环境"

这条线不占周次，但优先级高于第三个 side project。

- **为什么**：面试官最认"真实用户、真实数据、真实指标"。side project 再漂亮，也比不过"我在现产品里上了一个 LLM 功能，灰度 10%，满意度 xx"。
- **找场景**：客服问答 / 内部文档检索 / 代码助手 / 运营文案 / 工单分类——挑一个**边界清楚、失败可恢复**的。
- **做法**：1–2 周做内部 demo → 用真实数据建 20 条评测 → 小流量灰度 → 记录指标 → 复盘。
- **顺手收益**：内部转岗的筹码；简历上"生产环境 LLM 功能"这一行，比"个人项目"值钱。
- **注意**：公司数据合规、API Key 不进代码库、脱敏后再做评测。

## 十二、避坑与选修

**不做**：

- 不学微调（LoRA / SFT）、不深入 K8s、不考证书——岗位中低频，投入产出比低
- 不刷算法题海：每周 2 题保持手感即可，社招前端转岗看项目多于看题
- 不做第三个项目：两个做精 > 五个做烂
- 不追新框架：MCP / LangGraph 学会一个版本就够，原理比 API 值钱
- 不用 `as any` / `# type: ignore` 糊类型；不用"跑通一次"当验收

**选修（拿到 offer 后或空档期）**：

- vLLM / Ollama 本地部署 + 量化（1 周）
- LoRA 微调一个小模型（1 周，只为能聊明白）
- GraphRAG / LightRAG（3 天，知道解决什么问题）
- A2A（1 天，知道和 MCP 的分工）
- Dify 深入（2 天，能对比"平台 vs 手写"的取舍）

**避坑提醒**：

- 学练比 3:7：看 30 分钟就动手，别刷完教程再写
- 每周必须提交；"改动不提交"是最贵的坏习惯
- 评测不是最后一步，是每个项目的入场券
- 多 Agent 不是默认答案；能用 workflow 写死的，别交给模型自主决策
- 不要等"学完再投"：第 26 周有 P1 就投，面试是最好的复习

## 十五、在职执行说明（这一条比计划本身重要）

你是**在职前端**，不是脱产学生。整份计划的前提是：不辞职、不熬夜、可持续。

**定位**：目标不是"转纯后端"，而是"**能做 AI 应用全栈的前端**"——前端仍是你的门面和差异化，Python/FastAPI 只是补上的另一半。面试时讲"我能独立把 RAG/Agent 服务跑起来，也能把 ChatUI 做到生产级"，而不是"我转后端了"。

**时间**：

- 标准周 13–15 小时（周一至周四 1–1.5h + 周六 4h + 周日 4h）
- **忙周最低维持模式（4 小时）**：周内 2 次 × 1h 复习/清账 + 周末 2h 推进一小步。宁可慢，不要断。
- 加班 / 出差 / 上线周：只做"清账 + 复习"，不排新内容；回来先补欠账再前进。
- 32 周是理想节奏，实际按 34–36 周排也成立。**投递节点不变**（第 26 周有 P1 就投）——面试反馈比多学两周值钱。

**把工作变成学习**：

- 工作中的 AI 功能（哪怕只是内部工具）算本周产出，写进笔记和简历
- 优先争取：客服问答、内部文档检索、代码助手、运营文案——边界清楚、失败可恢复
- 公司数据合规、API Key 不进代码库、脱敏后再评测

**不辞职**：

- 在职转岗的谈判位置更好，也没有空窗期压力
- 先打听内部 AI 团队 / 项目，内部转岗是成本最低的路径；同时对外投递，两条腿走路

**每月校准**：

- 连续 2 周低于 4 小时 → 砍选修、保主线（Python + RAG + 评测 + 一个项目）
- 落后超过 3 周 → 把 32 周改成 36 周，投递节点不动
- 不要用"这周太忙"跳过 commit；commit 是最低的连续性证明

---

> 计划是地图，不是合同。每月复核一次，按 JD 改；但**第 13–20 周这条主线不要动**——那是从"会写后端"跨到"会做 AI 应用"的最小闭环。
