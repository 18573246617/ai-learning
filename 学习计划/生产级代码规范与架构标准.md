# 生产级代码规范与架构标准

> 用途：这是整个学习旅程的"代码基准"。所有练习、项目、产出都必须满足本文档的规范，目标是**学完的东西直接能写进生产代码**，架构和写法对齐市面上最主流的 Node.js + TypeScript 工程实践。
>
> 适用阶段：阶段一（Node.js 后端）起全程生效。第 1-3 周已写的代码不必立刻返工，但从第 4 周起的新代码一律按本标准执行，第 6 周做一次整体重构对齐。

---

## 一、技术选型（主流栈）

| 分类 | 选型 | 说明 |
|---|---|---|
| 语言 | TypeScript（strict） | 全程类型安全，不用 `any` |
| 运行时 | Node.js LTS（22+） | 长期支持版 |
| 包管理 | pnpm | 快、省磁盘、锁文件可靠 |
| Web 框架 | Express 5 | 生态最成熟，主流职位覆盖率最高 |
| 参数校验 | zod | 运行时校验 + 类型推断一体 |
| ORM / 数据库 | Prisma + PostgreSQL | 阶段二引入，行业事实标准 |
| 缓存 | Redis（ioredis） | 阶段二引入 |
| 日志 | pino | 结构化 JSON 日志，性能好 |
| 测试 | vitest + supertest | 阶段一第 5 周引入 |
| 代码质量 | ESLint（typescript-eslint）+ Prettier | 第 4 周立即引入 |
| 部署 | Railway / Vercel → Docker | 第 5-6 周起 |
| CI | GitHub Actions | 第 6 周起 |

**原则**：选型跟主流走，不追新不追偏。任何新依赖加入前，先想清楚"这是不是市场上普遍在用的"。

## 二、项目结构（分层架构）

目标结构（以阶段一的待办应用为例）：

```
src/
├── app.ts              # 组合根：只负责组装中间件 + 路由，返回 app，不做 listen
├── index.ts            # 启动入口：读配置、listen、优雅退出
├── config/             # 环境变量加载 + zod 校验（启动时缺失立即报错）
├── routes/             # 路由定义（尽量薄）：挂 controller，做参数校验
├── controllers/        # HTTP 层：取参数 → 调 service → 返回响应/状态码
├── services/           # 业务逻辑层：认证、任务规则（不碰 req/res，可单测）
├── repositories/       # 数据访问层：内存/文件/Prisma，只做存取
├── middleware/         # auth、validate、errorHandler、notFound、rateLimit、logger
├── schemas/            # zod schema（body/query/params 的 DTO）
├── utils/              # 纯函数工具（不依赖业务）
└── types/              # 全局类型扩展（如 req.user）
```

**依赖方向（只能从上往下依赖，禁止反向/跨层）**：

```
routes → controllers → services → repositories
```

- 路由和控制器不写业务规则（比如"密码不能和用户名相同"这种判断进 service）
- service 不碰 `req` / `res`，只接收数据、返回结果或抛业务错误
- repository 不写业务判断，只做存取
- 这样每一层都能单独测试，换数据库（内存 → Prisma）只动 repository 一层

> 过渡说明：第 2-3 周代码是 `routes + data` 两层，第 4 周保持现有代码继续推进新知识，第 6 周整合阶段按上图重构。

## 三、代码规范

### 命名

- 文件/目录：kebab-case（`error-handler.ts`）
- 变量/函数：camelCase（`findUserById`）
- 类/类型/接口：PascalCase（`AppError`、`CreateTaskInput`）
- 常量：UPPER_SNAKE_CASE（`JWT_EXPIRES_IN`）
- 布尔变量尽量用 `is` / `has` / `can` 开头（`isAdmin`）
- 接口名不加 `I` 前缀（主流 TS 风格）

### TypeScript 写法

- `strict: true` 必开；`tsc --noEmit` 必须零错误
- 禁止 `any`；确实不知道类型时用 `unknown` + 类型收窄
- 对外函数（service/controller）写显式返回类型
- 不用 `enum`，用联合类型 + `as const`（主流社区趋势，避免 `enum` 的运行时开销和双身份问题）
- `interface` 描述对象形状，`type` 描述联合/交叉/工具类型
- 类型尽量从 zod schema 推断（`z.infer`），避免手写两遍

### 错误处理（最重要的生产习惯）

1. 自定义错误基类：`AppError`（带 `statusCode`、`code`、`message`），业务错误用 `throw new AppError(401, 'UNAUTHORIZED', '请先登录')`
2. 用 `asyncHandler` 包装所有 async 路由，把错误统一交给 errorHandler，**不在路由里到处 try/catch**
3. 中央 errorHandler：记录错误日志（pino），返回 `{ code, message }`，**绝不把堆栈和内部信息返回给客户端**
4. 404 兜底：所有路由之后的 `notFoundHandler`，返回 404 JSON
5. 状态码语义：400 参数错误 / 401 未认证 / 403 无权限 / 404 不存在 / 409 冲突 / 500 兜底

### 输入校验

- body / query / params 全部用 zod 校验，在边界处拦截
- 用 `safeParse` + 统一 `validate` 中间件，校验失败返回 400 和友好错误信息
- 不要相信任何前端传来的数据，包括"看起来是数字"的 query 字符串（用 `z.coerce` / `z.enum().transform()` 处理）

### 安全基线

- 密码：bcrypt 哈希（成本因子 10-12），不存明文、不自己造哈希
- 认证：JWT + `Authorization: Bearer` 头，带过期时间；`JWT_SECRET` 只放环境变量
- 请求头规范用标准 Bearer，不用自定义头（如 `x-http-token` 是学习阶段的过渡写法，第 4 周切换）
- 日志里不打印密码、token、请求体
- 第 5 周起补：helmet 安全头、CORS 白名单、限流（express-rate-limit）

## 四、配置与环境变量（12-Factor）

- 所有可变配置（端口、密钥、数据库地址、API Key）走环境变量，不硬编码在代码里
- `src/config/` 用 zod 校验环境变量，启动时缺失/格式错立即报错（fail fast）
- `.env` 不入库，`.env.example` 入库（列出所有变量名和注释，不含真实值）
- 用 `node --env-file` 或 pino/配置模块统一加载
- 禁止把密钥提交进 git；`.gitignore` 里确认已排除 `.env`

---

## 五、日志

- 用 pino 结构化 JSON 日志，不用 `console.log`（生产日志要能机器检索）
- 请求日志中间件记录：method、path、status、耗时、requestId
- 分级：`info`（正常请求）、`warn`（预期内异常）、`error`（未预期异常，带堆栈）
- 日志落点在开发环境为可读格式，生产环境为 JSON

---

## 六、测试

- 框架：vitest + supertest
- 单测覆盖 service 层（业务规则，不启动服务器）
- 集成测试覆盖 API（supertest 起 app，测状态码、响应体、认证流程）
- 外部依赖（LLM API、第三方接口）一律 mock，测试不依赖网络
- 测试文件命名：`xxx.test.ts`，与被测文件同目录
- 阶段二接数据库后，测试用独立测试库/事务回滚，不污染开发数据

---

## 七、代码质量工具

第 4 周必须完成（不等第 6 周）：

- ESLint + typescript-eslint（推荐 `recommended` + `recommendedTypeChecked` 起步）+ Prettier
- package.json scripts 固定：
  - `lint`：ESLint 检查
  - `format`：Prettier 格式化
  - `check`：`tsc --noEmit` 类型检查
  - `test`：vitest 测试
- 配置文件和 ESLint/Prettier 冲突处理：`eslint-config-prettier` 关掉冲突规则
- 第 6 周起加 pre-commit 钩子（simple-git-hooks 或 husky）：提交前自动 lint + 类型检查

---

## 八、Git 与提交规范

- 提交信息用 Conventional Commits：`feat:` / `fix:` / `refactor:` / `docs:` / `chore:` / `test:`
  - 例：`feat: 注册接口接入 bcrypt 密码哈希`
- 每次练习/修复完成就提交，不留"旧账"
- `.env`、`node_modules`、构建产物不入库

---

## 九、部署与运维（第 5-6 周起）

- 12-Factor：环境配置化、无状态、可横向扩展
- 提供健康检查接口（`GET /healthz`），部署平台用它判断存活
- 优雅退出：收到 SIGTERM/SIGINT 后先停掉接收新请求，再关数据库连接等资源
- 生产构建：`tsc` 编译后跑编译产物（`node dist/index.js`），不用 tsx 跑生产
- 第 6 周起：Dockerfile + GitHub Actions（lint + typecheck + test 全绿才合并）

## 十、每周收尾"生产就绪"检查清单

每周末对照，全部通过才算本周闭环：

- [ ] `pnpm check`（tsc --noEmit）零错误
- [ ] `pnpm lint` 零错误（配置好后）
- [ ] `pnpm test` 通过（有测试的周）
- [ ] 代码里没有 `console.log`（一律 pino）
- [ ] 所有入参都过了 zod 校验
- [ ] 错误统一走 errorHandler，没有零散 try/catch + res.status
- [ ] 密钥/端口等配置在环境变量里，代码里没有硬编码
- [ ] `.env` 没被提交，`.env.example` 已更新
- [ ] git 提交信息符合 Conventional Commits
- [ ] 没有遗留 TODO/bug（有就记进待办并排期）
