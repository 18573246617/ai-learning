## 1. 本周全景：为什么是这六件事

阶段一还剩最后一周，产出物是"能拿出手的完整 API"。现在代码**功能齐全**（测试 18 个全绿、安全加固到位），但**结构还是第 2 周的"routes + data"两层**，第 4-5 周的新知识（JWT、bcrypt、pino、multer、限流）是直接往 router 里塞的。本周把整个 app 重构成生产级分层，同时补掉一直欠着的账：

| 现状（第 5 周结束时） | 问题 | 本周动作 |
|---|---|---|
| 业务逻辑（bcrypt 比较、jwt 签发）写在 `router/auth/index.ts` 里 | 路由太厚，无法单测业务 | 拆出 controllers + services |
| `service/auth`、`service/tasks`、`service/common/upload` 是 0 字节空壳 | 分层名存实亡 | 把业务规则下沉 service |
| `data/` 叫 data 不叫 repository | 命名不符合标准 | 改名 `repositories/` |
| 每个路由里 try/catch + `next(error)` | 样板代码重复、漏一处就 500 | `asyncHandler` + 自定义 `AppError` |
| `app.ts` 直接读 `process.env` | 缺配置校验，JWT_SECRET 忘配时启动不报错，登录才 500 | 加 `config/` 模块，启动 fail fast |
| `logger.ts` 用 `console.log` | 生产日志无法检索，违背标准 | 升级 pino 请求日志（状态码 + 耗时） |
| 没有 CI | 推上去没人把关 | GitHub Actions：lint + check + test + build 全绿 |

一句话记住本周：**让每一层只干一件事，让错误只有一个出口，让机器替你检查代码。**

## 2. 分层架构：routes → controllers → services → repositories

### 2.1 每层职责（背下来）

| 层 | 职责 | 能做什么 | 禁止做什么 |
|---|---|---|---|
| routes | 定义 URL 和中间件（含 zod 校验） | 挂 controller、挂 validate/checkAuth/upload | 写业务判断、直接调数据层 |
| controllers | HTTP 层：取参数 → 调 service → 定状态码和响应体 | `req.params`、`res.status()`、`res.json()` | 写业务规则、碰数据层 |
| services | 业务逻辑：认证、任务规则、密码比较 | 抛 `AppError`、返回结果 | 碰 `req/res`、做 HTTP 响应 |
| repositories | 数据存取：内存/文件/以后接 Prisma | 增删改查 | 写业务判断 |

依赖方向只能从上往下：`routes → controllers → services → repositories`。禁止反向（service 里 import router 就是架构事故）和跨层（controller 直接调 repository 也不行，第 6 周检查时会抓）。

目录结构
src/week2/
├── index.ts                # 启动入口
├── app.ts                  # 组合根
├── config/                 # ★ 新建：env 加载 + zod 校验（fail fast）
├── routes/                 # ★ router/ 改名：只挂 controller + 中间件
├── controllers/            # ★ 新建：取参数 → 调 service → res.json
├── services/               # ★ service/ 改名（加 s！）：业务逻辑
├── repositories/           # ★ data/ 改名：增删改查
├── middleware/             # 保留：checkAuth / errorHandler / logger / upload
├── schemas/                # 保留：zod 校验规则
├── utils/                  # ★ 新建：AppError / asyncHandler
└── types/                  # 保留

### 2.2 为什么这样分（面试要能说）

1. **可单测**：service 不碰 `req/res`，直接传参调用就能测业务规则，不用起服务器；
2. **可替换**：以后内存换 Postgres 只改 repositories 一层，services/controllers 一行不动；
3. **可分工**：后端团队天然按层分活，前端转后端面试官最认这个；
4. **好排查**：报错从哪层来一目了然（HTTP 错看 controller，业务错看 service，数据错看 repository）。

### 2.3 现在的代码 vs 重构后（以登录为例）

现在（第 5 周，全在 router 里）：
```ts
// router/auth/index.ts
authRouter.post('/login', loginLimiter, async (req, res, next) => {
    try {
        const result = await loginSchema.safeParse(req.body ?? {})
        if (!result.success) return res.status(400).json(result.error.flatten())
        const user = await findUser(result.data.username)          // ← 直接调数据层
        if (!user) return res.status(400).json({ message: '用户不存在' })
        const isMatch = await bcrypt.compare(result.data.password, user.password)  // ← 业务逻辑
        if (!isMatch) return res.status(400).json({ message: '用户名或者密码错误' })
        const token = jwt.sign({ userName: user.username }, process.env.JWT_SECRET!, { expiresIn: '8h' })
        res.json({ message: '登录成功', data: { username: user.username, token } })
    } catch (error) {
        next(error)
    }
})
```

目标（四层各管一段）：
```ts
// routes/auth.ts —— 只定义路由 + 中间件
router.post('/login', loginLimiter, validateBody(loginSchema), asyncHandler(authController.login))

// controllers/auth.controller.ts —— 取参数、调 service、回响应
export const authController = {
    login: async (req: Request, res: Response) => {
        const data = await authService.login(req.body)   // service 抛错就抛，不 try/catch
        res.json({ message: '登录成功', data })
    },
}

// services/auth.service.ts —— 业务规则，不碰 req/res
export const authService = {
    async login(input: LoginInput): Promise<{ username: string; token: string }> {
        const user = await userRepository.findByUsername(input.username)
        if (!user) throw new AppError(400, 'USER_NOT_FOUND', '用户不存在')
        const isMatch = await bcrypt.compare(input.password, user.password)
        if (!isMatch) throw new AppError(400, 'BAD_CREDENTIALS', '用户名或者密码错误')
        const token = jwt.sign({ userName: user.username }, config.jwtSecret, { expiresIn: JWT_EXPIRES_IN })
        return { username: user.username, token }
    },
}
```

注意登录接口的"用户不存在"和"密码错误"返回相同提示是安全惯例（防枚举用户名），这个判断要写进 service 还是 controller，自己想一下——答案是 service，因为它是业务规则。

## 3. 自定义错误类 AppError + asyncHandler

### 3.1 为什么

现在每个路由 try/catch，错误处理散落；`errorHandler` 只能靠猜（`instanceof multer.MulterError`、错误消息包含"文件类型"…）。生产做法是：**业务代码主动抛带语义的错误对象，错误处理只认这一种**。

### 3.2 模板（新建 `src/week2/utils/errors.ts`）

```ts
export class AppError extends Error {
    constructor(
        public readonly statusCode: number, // HTTP 状态码：400/401/403/404/409/500
        public readonly code: string,       // 业务错误码：'USER_NOT_FOUND' 等，前端/排查用
        message: string,
    ) {
        super(message)
        this.name = 'AppError'
    }
}
```

用法：`throw new AppError(401, 'UNAUTHORIZED', '请先登录')`

### 3.3 asyncHandler 模板（`src/week2/utils/async-handler.ts`）

Express 5 本身能接住 async 路由的 rejected promise，但为了统一风格（且 Express 4 项目是主流，面试常问），还是包一层，让所有 async handler 的错误都走 `next`：

```ts
import type { NextFunction, Request, RequestHandler, Response } from 'express'

export const asyncHandler =
    (fn: (req: Request, res: Response, next: NextFunction) => Promise<unknown>): RequestHandler =>
    (req, res, next) => {
        fn(req, res, next).catch(next)
    }
```

### 3.4 errorHandler 升级（`src/week2/middleware/errorHandler.ts`）

升级后逻辑只有一条主线：

```ts
// 伪代码（自己写完整版）

}
// 未知错误：pino.error 记堆栈，返回 500，绝不把堆栈给客户端
```

## 5. 补漏：config 模块 + pino 日志

### 5.1 config 模块（`src/week2/config/index.ts`）

目的：启动时校验环境变量，缺失立即报错（fail fast），而不是等登录接口 500 才发现 JWT_SECRET 没配。这也是第 4 周欠的账。

```ts
import { z } from 'zod'

const envSchema = z.object({
    PORT: z.coerce.number().default(1300),
    JWT_SECRET: z.string().min(32, 'JWT_SECRET 必须配置且至少 32 位'),
    CORS_ORIGINS: z.string().default(''),
})

const parsed = envSchema.safeParse(process.env)
if (!parsed.success) {
    console.error('环境变量配置错误:', parsed.error.flatten().fieldErrors)
    process.exit(1)   // fail fast：配置错了就别启动
}

export const config = {
    port: parsed.data.PORT,
    jwtSecret: parsed.data.JWT_SECRET,
    corsOrigins: parsed.data.CORS_ORIGINS.split(',').map((s) => s.trim()).filter(Boolean),
}
```

然后把 `app.ts` 里读 `process.env.CORS_ORIGINS`、`index.ts` 里读 `process.env.PORT`、auth service 里读 `process.env.JWT_SECRET` 全部改成 `config.xxx`。

> 坑：测试进程不走 `--env-file`，但测试文件里已经自己设了 `process.env.JWT_SECRET`——config 模块在测试里也会执行，所以测试能过。如果某个测试文件忘了设，会直接 `process.exit(1)`，报错信息会告诉你哪个变量缺，这就是 fail fast 的价值。

### 5.2 pino 请求日志（`src/week2/middleware/logger.ts`）

现在只有 `console.log('${req.method} ${req.url}')`，生产标准要求：method、path、status、耗时、requestId。pino 的 `logger.info({ ... })` 输出 JSON：

```ts
import pino from 'pino'
import type { Request, Response, NextFunction } from 'express'

const logger = pino()

export const loggerMiddleware = (req: Request, res: Response, next: NextFunction) => {
    const start = Date.now()
    res.on('finish', () => {
        logger.info({
            method: req.method,
            path: req.url,
            status: res.statusCode,
            durationMs: Date.now() - start,
        })
    })
    next()
}
```

## 7. GitHub Actions CI（本周压轴）

### 7.1 为什么需要 CI

本地全绿不算数——换台机器、换个环境可能就红。CI = 每次 push 自动跑一遍 `lint + check + test + build`，红了就不该合并。面试问"你的项目有 CI 吗"，这周之后你能说"有，GitHub Actions 全绿"。

### 7.2 建 `.github/workflows/ci.yml`（在仓库根目录 `D:\AI学习\.github\workflows\ci.yml`）

```yaml
name: CI

on:
  push:
    branches: [master, main]
  pull_request:

jobs:
  ci:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: 代码练习/阶段一-Node.js后端
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 11.19.0

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
          cache-dependency-path: 代码练习/阶段一-Node.js后端/pnpm-lock.yaml

      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm check
      - run: pnpm test
      - run: pnpm build:week2
```

### 7.3 练习 7（30 分钟）

1. 建上面的 workflow 文件
2. 本地提交所有改动：`git add -A && git commit -m "refactor: 第六周分层重构 + CI"`，推 GitHub：`git push github master`
3. 打开 GitHub 仓库 → Actions 页签，等第一个 job 跑完
4. **必须看到全绿**。红了就点进 job 看哪一步挂，对照第 7.4 排查

### 7.4 常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| `ERR_PNPM_OUTDATED_LOCKFILE` | lockfile 和 package.json 不一致 | 本地 `pnpm install` 后提交 lockfile；CI 里用 `--frozen-lockfile` |
| pnpm 版本报错 | CI 默认 pnpm 版本不对 | `pnpm/action-setup` 里固定 `version: 11.19.0` |
| bcrypt/esbuild 构建失败 | pnpm 11 默认拦截构建脚本 | `pnpm-workspace.yaml` 里的 `allowBuilds` 要提交上去 |
| 测试失败：登录 429 | 限流中间件跨测试共享 | 每个测试文件请求数少就没事；如果加了用例超了 10 次登录，`beforeEach` 重置或把登录限流在测试环境调大 |
| 中文路径 `working-directory` 报错 | Actions runner 罕见情况 | 备选：把后端代码单独推一个仓库（部署指南 2.2 备注的做法），根目录跑 CI |

## 8. 加分练习（做完主线再碰）
