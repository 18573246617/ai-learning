## 1. 为什么要写测试

手动测试的问题：改一处代码，不知道哪里坏了；接口越来越多，全靠 Postman 点一遍不现实。面试和真实团队里，"项目有没有测试、会不会写测试"是基本要求。

测试分三层：

| 层级 | 测什么 | 工具 |
|---|---|---|
| 单元测试 | 单个函数 / service（不启动服务器） | vitest |
| 集成测试 | API 接口（起 app、发请求、查响应） | vitest + supertest |
| 端到端 | 整个系统（数据库、外部依赖全真的） | 本周不做 |

本周做前两层，重点是**冒烟测试**：核心流程跑通——注册 → 登录 → 拿 token → 访问受保护接口。


### 2.5 关键坑：内存数据会串

你的数据是模块里的内存数组，多个测试跑下来数据会互相污染（第一个测试注册的用户，第二个测试还能看到）。解决思路：

- 导出一个 `reset()` 之类的函数，`beforeEach` 里清空数据
- 这暴露了一个设计问题：**数据层要"可重置、可注入"**，第 6 周重构 repository 时会彻底解决

## 3. mock 外部请求（为 AI 应用打基础）

为什么 AI 应用开发**特别依赖 mock**：LLM API 贵、慢、有频率限制，测试不可能真调。等你做 RAG 和 Agent 时，所有外部调用都要 mock 掉。

基本用法：

```ts
import { vi } from 'vitest'
import {callLLm} from '../../llm'

const mockFetch = vi.fn().mockResolvedValue({
  ok: true,
  json: async () => ({ choices: [{ text: '你好' }] }),
})




//1.对于import导入的这种情况可以使用vi.mock('导入的路径',vi.fn().mockResolveValue('模拟返回数据'))进行替换测试，一般在router层
vi.mock( '../../llm',()=>({
  callLLm:vi.fn().mockResolveValue('模拟返回数据')
}))


//2.对于全局性的api 例如node自带的featch请求可以使用vi.stubGlobal('api名称',vi.fn().mockResolveValue('模拟返回的数据')) 也可以使用vi.mock

vi.stubGlobal('fetch',vi.fn().mockResolveValue('模拟返回的数据'))
// 在设置全局的时候要使用afterEach 里 vi.unstubAllGlobals() 恢复全局
// 或者
vi.mock('node-fetch',()=>({
 default: vi.fn().mockResolveValue({}) //此处需要使用default
}))

// expect(result).toBe('你好，我是AI')	result 严格等于（===）这个字符串	问：结果是不是这个值？
// expect(fetch).toHaveBeenCalledTimes(1)	fetch 这个 mock 函数被调用了 1 次	问：假电话响了几次？
// expect(fetch).toHaveBeenCalledWith(url, ...)	fetch 被调用时参数对不对（url 完全匹配）	问：是不是拨的这个号码？
// expect.objectContaining({ method: 'POST' })	第二参数只要包含 method: 'POST' 就算过（不管有没有其他字段）	问：请求方式是不是 POST？（其他字段不关心）
// await expect(callLLM('你好')).rejects.toThrow('LLM 调用失败: 429')	这个 Promise 必须失败（reject），且错误消息包含指定文本	问：是不是按预期炸了？炸得对不对？
```

`vi.fn()` 造一个假函数，断言它**被调用过、参数对、返回预期结构**；`vi.mock()` 可以替换整个模块。只能对 import使用

## 4. multer 文件上传

### 4.1 安装

```bash
pnpm add multer            # 运行时依赖
pnpm add -D @types/multer  # 类型声明（dev 依赖，编译产物不需要）
```

- **multer 是什么**：Express 生态里最主流的 **multipart/form-data 表单解析中间件**。普通 JSON 请求用 `express.json()` 解析就够了，但**文件只能通过 multipart 表单传**（浏览器 `<input type="file">` 就是这么发的），而 Express 内置解析器不认这种格式，所以需要 multer。
- **底层原理**：multer 内部基于 busboy 流式解析 multipart 数据（`node_modules/multer` 里能看到这个依赖）。面试问"文件上传原理"答到这一层就够。
- 装完在 `app.ts` / router 里导入使用，完整示例见 4.2.5。

### 4.2 核心概念

#### 4.2.1 四种解析粒度

multer 暴露一个 `upload` 对象，不同方法对应不同字段组合（"粒度" = 一个请求里最多怎么收文件）：

| API | 适用场景 | 解析结果 |
|---|---|---|
| `upload.single('file')` | 表单里只有一个文件字段 | 文件挂到 `req.file`（**本周用这个**） |
| `upload.array('files', 5)` | 多个文件共用一个字段名 | 挂到 `req.files`（数组），第 2 参限最多 5 个 |
| `upload.fields([{ name: 'avatar' }, { name: 'photos', maxCount: 3 }])` | 多个不同字段名混传 | 挂到 `req.files`（对象，key 是字段名） |
| `upload.none()` | 只传普通文本字段、不传文件 | 只解析文本到 `req.body` |

##### ① `upload.single('file')`：最常用，一次收一个文件

前端对应的 FormData 写法（**key 必须和 single() 里的字符串一致**）：

```ts
// 浏览器端
const formData = new FormData()
formData.append('file', fileInput.files[0])  // key 'file' 要跟 single('file') 对上
formData.append('caption', '一只猫')          // 普通文本字段照常加
await fetch('/upload', { method: 'POST', body: formData })
// ⚠️ 千万别手动设 Content-Type！浏览器会自动带 multipart/form-data; boundary=...，
//    手写会丢掉 boundary 分隔符，服务端直接解析失败
```

后端结果：文件在 `req.file`（单个对象），文本字段在 `req.body.caption`。

坑：前端对**同一个 key** `append` 了多个文件时，`single` 只取第一个，其余**静默丢弃**（不报错，容易排查半天）。

##### ② `upload.array('files', 5)`：多个文件共用一个 key

前端完整流程（关键：**同一个 key 逐个 append，而不是塞整个 FileList**）：

```html
<!-- 必须加 multiple 属性，用户才能多选 -->
<input type="file" multiple id="fileInput">
```

```ts
// ① 拿到用户选的多个文件（FileList，可遍历）
const files = (document.getElementById('fileInput') as HTMLInputElement).files!

// ② 同一个 key 'files' 逐个 append（关键！）
const formData = new FormData()
for (const file of files) {
  formData.append('files', file)   // key 全部叫 'files'，追加 N 次
}

// ③ 发送（别手动设 Content-Type，浏览器自动带 boundary）
await fetch('/upload', { method: 'POST', body: formData })
```

底层报文就是 `name="files"` 出现多次，multer 按出现顺序收进数组：

```
------boundary
Content-Disposition: form-data; name="files"; filename="a.png"
（a.png 内容）
------boundary
Content-Disposition: form-data; name="files"; filename="b.png"
（b.png 内容）
------boundary--
```

坑：`formData.append('files', files)` 直接把整个 FileList 塞进去是**不行的**——append 只接受 `string / Blob / File`，传 FileList 会报错或静默失败，必须**循环逐个 append**。

后端结果：`req.files` 是**数组**，顺序 = append 顺序 = 报文顺序，每个元素结构和 `req.file` 一样。

- 第 2 个参数 `5` 是**最多数量**：超过会抛 `MulterError`（`code: 'LIMIT_UNEXPECTED_FILE'`），走错误处理中间件
- 注意：`limits: { fileSize }` 是**每个文件**的大小上限，不是这批文件的总大小（总上限 = 数量 × 单文件上限）

##### ③ `upload.fields([...])`：不同 key 混着传（"头像 + 相册"这类场景）

```ts
const formData = new FormData()
formData.append('avatar', avatarFile)          // 单张头像
formData.append('photos', photo1)              // 多张照片
formData.append('photos', photo2)
```

后端结果：`req.files` 是**对象**，key 对应字段名：

```ts
req.files
// {
//   avatar: [ { 和 req.file 同结构 }, ],   // ⚠️ 值永远是数组！即使只有 1 个
//   photos: [ { ... }, { ... } ],
// }
```

- `maxCount` 可以按字段单独限制：`{ name: 'photos', maxCount: 3 }`
- 取单张：`req.files.avatar[0]`（记得先判空，用户可能没传头像）

##### ④ `upload.none()`：纯文本字段（没文件）

适用场景：某些前端组件**即使没文件也用 FormData 提交**（Content-Type 仍是 multipart），这时 `express.json()` 解析不了，得靠它收文本字段。

- 结果：只有 `req.body`，`req.file` / `req.files` 都是 `undefined`
- 坑：这种请求里**混进了文件**，会抛 `LIMIT_UNEXPECTED_FILE`

##### 选择口诀

- 单文件 → `single`；多文件同 key → `array`；多文件多 key → `fields`；没文件只是 multipart 文本 → `none`

> 本质：四个方法**共用同一个解析器**，区别只是"字段名匹配规则 + 结果挂到 req.file 还是 req.files"。字段名对不上（比如 single 收到别的 key）一律抛 `LIMIT_UNEXPECTED_FILE`——记住这个 code，出错时一眼定位。

#### 4.2.2 解析后文件在哪：`req.file`

`upload.single('file')` 是**中间件**，执行完会把文件信息挂到 `req.file`，后面的路由处理器直接读：

```ts
{
  fieldname: 'file',          // 表单字段名，对应 single('file') 里的 'file'
  originalname: 'cat.png',    // 用户电脑上的原始文件名（⚠️ 不能直接用，见 4.3）
  encoding: '7bit',           // 编码方式，一般不用管
  mimetype: 'image/png',      // 浏览器按文件类型自报的（⚠️ 可伪造，不可全信）
  size: 12345,                // 字节数
  destination: 'uploads/',    // diskStorage：落盘目录
  filename: 'a1b2c3....png',  // diskStorage：服务器上实际文件名（你改过的）
  path: 'uploads/a1b2c3....png', // diskStorage：完整路径
  buffer: <Buffer ...>        // memoryStorage：文件内容（内存）
}
```

> 注意：`destination` / `filename` / `path` 只有 `diskStorage` 有，`buffer` 只有 `memoryStorage` 有——**两者二选一，不会同时出现**。

#### 4.2.3 两种存储方式对比

| | diskStorage（磁盘） | memoryStorage（内存） |
|---|---|---|
| 文件放哪 | 服务器 `uploads/` 目录 | 内存 `req.file.buffer` |
| 怎么取 | 按 `path` 再用 fs 读 | 直接 `req.file.buffer`，无 IO |
| 优点 | 落盘即持久化，重启不丢 | 快；不占磁盘 |
| 缺点 | 磁盘 IO，要自己管目录和清理 | 占内存，大文件会爆内存，重启就丢 |
| 适合场景 | 本地长期保存（**本周用这个**） | 收到后马上转给云存储 / LLM（阶段三常用） |

**怎么选**：文件只是"中转"（比如接收后立刻传给 LLM 或 OSS），用 memoryStorage 最顺；要长期存服务器上，用 diskStorage。

#### 4.2.4 diskStorage 完整配置

```ts
import multer from 'multer'
import {extname} from 'node:path'
import {randomBytes} from 'crypto'
import {mkdirSync} from 'fs'

const upload=multer({
  storage:multer.diskStorage({
    filename:(req,file,cb)=>{
      const ext=extname(file.orignalname)
      cb(null,randomBytes(16).toString('hex')+ext)
    },
    destination:(req,file,cb)=>{
       mkdirSync('uploads',{recursive:true})
       cb(null,'uploads/')
    }
  }),
  limits:{
    fileSize: 2 * 1024 * 1024, // 单文件 ≤ 2MB
    files: 5, // 单次最多 5 个文件
    fields: 10, // 非文件字段 ≤ 10 个
    fieldSize: 512 * 1024, // 非文件字段值 ≤ 512KB
    fieldNameSize: 100, // 字段名 ≤ 100 字符
    parts: 20, // 总 parts ≤ 20  
  },
  fileFilter:(req: Request, file: Express.Multer.File, cb: multer.FileFilterCallback) => {
    if (file.mimetype === "image/jpeg" || file.mimetype === "image/png") {
        cb(null, true)
    } else {
        cb(new Error("文件类型错误"))
    }
  }
})

upload.single('file')
upload.array('file',5)
upload.fields([
  { name: "file",  maxCount: 1 },
  { name: "file2", maxCount: 3 },
])

import path from 'node:path'
import { randomBytes } from 'node:crypto'

  filename: (req, file, cb) => {
    const ext = path.extname(file.originalname)      // 取扩展名 '.png'
    cb(null, randomBytes(16).toString('hex') + ext)  // 随机名+扩展名，不用原名！
  },
})

// ② 大小限制：2MB（单位是字节）
const limits = { fileSize: 2 * 1024 * 1024 }

// ③ 类型过滤：只放行 jpg/png
const fileFilter = (req: Request, file: Express.Multer.File, cb: multer.FileFilterCallback) => {
  if (file.mimetype === 'image/jpeg' || file.mimetype === 'image/png') {
    cb(null, true)                    // 放行
  } else {
    cb(new Error('只支持 jpg/png 图片'))  // 拒绝 → 交给错误处理中间件
  }
}

// ④ 组合成一个中间件，路由里直接用
const upload = multer({ storage, limits, fileFilter })
```

**回调套路**：`destination` / `filename` / `fileFilter` 都是 `(req, file, cb)`，`cb(null, 值)` 表示成功，`cb(new Error(...))` 表示失败——error-first 回调风格，别记错参数顺序。

#### 4.2.5 在路由里怎么用

```ts
import { Router } from 'express'
import multer from 'multer'
// 建议把 4.2.4 的 storage/limits/fileFilter 抽到单独文件 multer.config.ts 里，路由处只组装
const upload = multer({ storage, limits, fileFilter })

router.post('/upload', upload.single('file'), (req, res) => {
  // 走到这里，multer 已经解析完：
  // - 文件信息在 req.file（含随机文件名 path）
  // - 普通文本字段在 req.body
  res.json({ code: 0, data: { url: `/uploads/${req.file.filename}` } })
})
```

> ⚠️ 中间件顺序：`upload.single('file')` 必须放在路由处理器**之前**——它先解析请求体，你的处理函数才能读到 `req.file`。这就是"中间件链"的典型例子。

#### 4.2.6 大小限制和类型过滤是"双保险"

- `limits.fileSize`：**超了直接抛 `MulterError`**（`code: 'LIMIT_FILE_SIZE'`），和 fileFilter 是两个独立检查
- `fileFilter`：在文件写入**前**拦截，用 `file.mimetype` 判断（⚠️ mimetype 是浏览器自报、可伪造，只能当第一道防线，真正校验得读文件头，本周不展开）

**缺一不可**：只有 fileFilter 的话，超大图片照样传满磁盘；只有 limits 的话，恶意文件照样能传进来。

#### 4.2.7 底层原理：busboy 是怎么"流式解析"的

##### ① multipart 报文长什么样

用 `<input type="file">` 上传时，浏览器发的请求体不是 JSON，而是一段**用 boundary 分隔符切开**的文本（抓包能看到）：

```
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxk

------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="file"; filename="cat.png"
Content-Type: image/png

（这里是图片的二进制内容，一大坨）
------WebKitFormBoundary7MA4YWxk
Content-Disposition: form-data; name="caption"

一只猫
------WebKitFormBoundary7MA4YWxk--
```

要点：

- `boundary=...` 是**分隔符**，服务端靠它把请求体切成一段一段
- 每段 = 自己的小 header（`Content-Disposition` 里带字段名 `name` 和文件名 `filename`）+ 空行 + 内容
- 最后一段以 `--` 结尾表示"完了"

##### ② 为什么要"流式"：文件可能很大

文件可能是几百 MB，**不能也不该一次性全读进内存**。所以 busboy 的做法：请求体（`req` 本身就是一个可读流，week3 学过）通过 `req.pipe(busboy)` 喂进去，**边读边切**——每读完一段就立刻触发事件通知外面处理，处理完这段再继续读下一段，全程内存里只存"当前这一段"。

##### ③ busboy 的核心：三个事件

```ts
import busboy from 'busboy'

const bb = busboy({ headers: req.headers, limits: { fileSize: 2 * 1024 * 1024 } })

bb.on('field', (fieldname, value) => {
  // 读到普通文本字段（如上面的 caption）
  req.body[fieldname] = value
})

bb.on('file', (fieldname, fileStream, filename, encoding, mimetype) => {
  // 读到文件字段！fileStream 本身又是一个可读流，文件内容一段段流进来
  // 注意：这里不会等文件全部读完，是"来一段处理一段"
  fileStream.on('data', chunk => { /* 处理这一段二进制 */ })
  fileStream.on('end', () => { /* 这个文件读完了 */ })
  fileStream.on('limit', () => { /* 超了 limits.fileSize，触发 */ })
})

bb.on('finish', () => {
  // 整个请求体解析完了，可以组装结果、继续走下一个中间件
  next()
})

req.pipe(bb)   // 把请求体这个可读流"接"到 busboy 上
```

##### ④ multer 在这之上只做了三件事

busboy 只负责"解析"，不管文件存哪。multer 就是**给 busboy 装了个存储插槽**（storage）：

| 配置 | multer 在 file 事件里做的事 | 依赖的 busboy 概念 |
|---|---|---|
| `memoryStorage` | 每段 chunk 存进数组，`end` 时 `Buffer.concat` 拼成完整 buffer | 文件流 `data` / `end` |
| `diskStorage` | `fs.createWriteStream(目标路径)`，然后 `fileStream.pipe(writeStream)` 直接落盘 | 文件流 `pipe` 到写流 |
| `limits` | 监听文件流的 `limit` 事件 → 抛 `MulterError` | 文件流 `limit` 事件 |
| `fileFilter` | 写入前判断 mimetype，拒绝就丢弃这段流 | 文件流刚开始时 |

所以 multer 本质 = **busboy（解析器）+ storage（落盘 / 进内存的策略）+ 一点事件编排**。面试被追问"文件上传原理"，把 ②③④ 讲出来就稳了。

### 4.3 生产要点（重点，面试爱问）

1. **不能信任文件名**：用户传 `../../etc/passwd` 这种名字会路径穿越。必须用 `randomBytes` 生成新文件名
2. **限制大小和类型**：`limits` + `fileFilter` 双保险
3. **MulterError 要识别**：超大小会抛 `MulterError`，你的 errorHandler 不识别它就会返回 500，要单独处理成 400/413
4. **上传目录独立**：存到 `uploads/`，并加进 `.gitignore`

## 5. 安全加固：helmet / CORS / 限流

### 5.1 helmet：一行加安全头

```ts
import helmet from 'helmet'
app.use(helmet())
```

```text
自动加 `X-Content-Type-Options`（防 MIME 嗅探）、`X-Frame-Options`（防点击劫持）、HSTS 等。面试能说出 2-3 个它设置的头就算过关。

helmet 是什么
它本质是一个中间件集合（内部是十几二十个小中间件），每个小中间件负责设置一两个安全头。默认调用 helmet() 会全部启用，也可以通过传参禁用/配置其中某几个。
它主要设置的安全头（面试重点）
1. X-Content-Type-Options: nosniff —— 防 MIME 嗅探
问题：浏览器在收到响应时，如果没写 Content-Type 或写得含糊，会尝试"猜"文件类型（MIME 嗅探）。攻击者可以上传一个伪装成图片的 HTML/JS（比如名字叫 cat.png，内容是 <script>）
解决：nosniff 告诉浏览器"别猜，老老实实按响应头里的 Content-Type 解析"。你的上传接口只允许图片（笔记 5 的 multer 部分），正是配合这一层防御。

2. X-Frame-Options: SAMEORIGIN（或 DENY）—— 防点击劫持
问题：攻击者在自己网站用 <iframe src="你的网站"> 嵌入你的页面，再在上面盖一层透明的诱导按钮。用户以为在点"领取优惠"，实际点的是你站上的"删除/转账"按钮。
解决：SAMEORIGIN 允许同源页面嵌入，禁止跨域 iframe；DENY 是任何站点都不许嵌入。注意：如果你的页面合法地需要被别的网站 iframe（比如嵌入第三方地图、支付页），就不能用这个，得改用 CSP 的 frame-ancestors。
3. Strict-Transport-Security（HSTS）—— 强制 HTTPS
问题：用户手输 http://你的域名 或点旧链接，浏览器会先用明文 HTTP 请求一次，这次请求可能被中间人劫持。
解决：浏览器收到 HSTS 头后，记住"这个域名只能走 HTTPS"（有效期由 max-age 控制，默认约 180 天），以后自动把 HTTP 升级成 HTTPS，彻底杜绝那一次明文请求。
注意：它只在 HTTPS 响应里才生效，本地开发（http://localhost）测不到是正常的。
4. Content-Security-Policy（CSP）—— 最强大的头
白名单机制：规定页面能加载哪些来源的脚本、样式、图片、连接。比如 default-src 'self' 表示只允许同源资源。
价值：即使攻击者注入了恶意脚本（XSS），CSP 也能阻止它加载/执行，是 XSS 的兜底防线。
坑：这个头也是最容易把项目搞挂的——如果你的前端用了 CDN 脚本、内联样式、eval()、WebSocket、Google Fonts，都可能被 CSP 拦掉。所以实际项目里通常要按环境精细配置，而不是用默认值。
5. 其他常用头
头	作用
X-XSS-Protection	老式浏览器的 XSS 过滤器（现代浏览器已弃用，CSP 取代了它）
Referrer-Policy	控制跳转时 Referer 泄露多少信息，防隐私泄露
Cross-Origin-Opener-Policy / Cross-Origin-Resource-Policy	跨源隔离相关，防 Spectre 类攻击
X-Permitted-Cross-Domain-Policies	禁止 Flash/PDF 跨域读你的资源

```

### 5.2 CORS：白名单

**为什么会有 CORS**：浏览器的同源策略规定，页面只能读取“同源”（协议 + 域名 + 端口三者一致）的响应。

- 前端 `http://localhost:5173`（Vite）→ 后端 `http://localhost:1300`：**端口不同 = 跨源**
- 关键认知：请求其实**发出去了**，后端也正常处理了，但浏览器发现响应头里没有 `Access-Control-Allow-*`，就把响应**吞掉**并报 CORS error
- 所以：**CORS 是浏览器拦截，不是服务器拒绝**（curl / Postman 永远没有 CORS 问题，原因就在这）

**简单请求 vs 预检请求**：

| 类型 | 触发条件 | 行为 |
|---|---|---|
| 简单请求 | GET/POST/HEAD，Content-Type 是 `text/plain`、表单或 `multipart/form-data`，无自定义头 | 直接发，浏览器只检查响应头 |
| 预检请求 | 带 `Authorization` 头、自定义头、`Content-Type: application/json` | 浏览器先发一个 `OPTIONS` 请求试探，服务器回应允许后，才发真实请求 |

> ⚠️ 带 `Authorization: Bearer xxx` 的请求**一定是预检请求**。CORS 没配好时的典型现象：前端报“请求失败”，后端日志里什么都没有——请求被预检拦在门外了。
**安装**：

```bash
pnpm add cors
pnpm add -D @types/cors
```

**开发环境：直接放开所有源**：

```ts
import cors from 'cors'
app.use(cors())
```

`app.use(cors())` 本质是自动给响应加三件套：

- `Access-Control-Allow-Origin: *`
- `Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE`
- `Access-Control-Allow-Headers: Content-Type, Authorization` ← **关键：放行预检用的自定义头**

**生产环境：白名单，且从环境变量读（符合 12-Factor）**：

```ts
import cors from 'cors'

const origins = (process.env.CORS_ORIGINS ?? '')
  .split(',')
  .map(s => s.trim())
  .filter(Boolean)

app.use(cors({
  origin(origin, callback) {
    // 无 origin 的请求（curl / Postman / 同源页面）直接放行
    if (!origin || origins.includes(origin)) {
      callback(null, true)
    } else {
      callback(new Error('不允许的跨域来源'))
    }
  },
  credentials: true, // 需要携带 Cookie 时开启
}))



// 写法 1：布尔值 —— 全部放行 / 全部拒绝
app.use(cors({ origin: true }))    // 等价于 app.use(cors())

// 写法 2：字符串 / 数组 —— 静态白名单
app.use(cors({ origin: 'https://myapp.com' }))
app.use(cors({ origin: ['https://a.com', 'https://b.com'] }))

// 写法 3：函数 —— 动态判断（你的笔记用的这种）
app.use(cors({ origin(origin, callback) { ... } }))
```

```env
# env/.env.development
CORS_ORIGINS=http://localhost:5173
```

**为什么白名单必须从环境变量读**：12-Factor 第 3 条“配置与代码分离”——同一份代码要在开发/测试/生产三个环境跑，白名单各不相同，写死在代码里就废了。这和项目里 `PORT`、`JWT_SECRET` 走同一套 `--env-file` 加载模式。

**常见坑**：

1. `credentials: true` 时 `origin` 不能是 `'*'`——浏览器规定带 Cookie 的跨域请求，`Access-Control-Allow-Origin` 必须是**具体源**，`*` 直接报错。这是生产必须用白名单的另一个原因
2. 白名单注意尾斜杠：`https://myapp.com` 和 `https://myapp.com/` 是不同 origin，容易踩
3. CORS 只防“别的网站浏览器读你的响应”，防不了 curl / Postman / 爬虫直接调——**真正的门禁是 JWT 鉴权**，CORS 只是配合
4. 白名单外来源会 `callback(new Error(...))`，会走到错误处理中间件，所以 errorHandler 必须在最后

**面试点**：能说清这三条就算过关——① CORS 是浏览器行为，不是服务器拒绝；② 带自定义头的请求会触发 OPTIONS 预检；③ 白名单 + `credentials: true` 时 origin 不能是 `*`。

### 5.3 限流：防暴力破解

**为什么需要限流**：

1. **暴力破解**：攻击者拿字典疯狂试密码，登录接口不限流，迟早试中一个弱密码（bcrypt 防的是“拖库后反推”，防不了“在线爆破”这个动作）
2. **爬虫**：把整站数据抓走
3. **刷接口 / DoS**：恶意请求打爆服务器（短信轰炸、占库存、耗尽带宽）

**安装**：

```bash
pnpm add express-rate-limit
```

**原理**：express-rate-limit 在内存里维护一个计数器，按 **IP + 路径** 记录每个时间窗口内的请求次数，超过额度直接返回 **429 Too Many Requests**，不再往下走路由。

**① 全局限流：所有接口一个基础额度**（挂最前面，先于所有路由）：

```ts
import { rateLimit } from 'express-rate-limit'

const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,   // 时间窗口：15 分钟
  limit: 100,                 // 窗口内最多 100 次（v7 起用 limit，旧版 max 已废弃）
  standardHeaders: 'draft-8', // 在响应头暴露 RateLimit-Limit / RateLimit-Remaining 等标准头
  legacyHeaders: false,       // 关掉旧版 X-RateLimit-* 头（v7 默认 true，会有两套头）
})

app.use(limiter) // 放在所有路由之前
```

**② 登录接口单独更严：1 分钟最多 10 次**（全局限流之上再叠一层）：

```ts
const loginLimiter = rateLimit({
  windowMs: 60 * 1000, // 1 分钟
  limit: 10,           // 最多 10 次
  standardHeaders: 'draft-8',
  legacyHeaders: false,
  // 超出后返回给前端的提示（默认是一段纯文本，改成 JSON 跟项目其他接口一致）
  message: { message: '登录尝试过于频繁，请 1 分钟后再试', data: null },
})

app.use('/auth/login', loginLimiter) // 只挡登录这一个接口，且必须在路由处理之前
```

**注意区分**：全局限流管“服务器不被刷挂”，登录限流管“密码不被爆破”，两者目的不同、额度不同、要同时上。

**429 状态码**：RFC 标准语义就是“请求太多”，客户端看到它应该自动退避（过一会儿再重试）。

**常见坑**：

1. **反向代理后 IP 全一样**：部署到 Nginx / 云厂商后面时，请求的 IP 全是代理的 IP，限流会把所有用户算成同一个人 → 必须 `app.set('trust proxy', 1)` 让 Express 从 `X-Forwarded-For` 头里取真实 IP。本地开发不用管
2. **内存存储的局限**：计数器存在进程内存里 → 重启就清零；多实例部署时每个实例各记各的（等于额度 × N）→ 生产分布式要换 Redis 存（`rate-limit-redis` 包）
3. **限流会误伤**：公司 NAT 出口是同一个公网 IP，全公司共享额度 → 额度要留余量
4. 限流中间件要在 `app.use(helmet())` 之后、路由之前挂；被限流时不会进路由，所以**不会走到 errorHandler**

**面试点**：能说出——① 限流是为了防暴力破解 / 爬虫 / 刷接口；② 全局限流 + 登录单独更严的双层策略；③ 超限返回 429；④ 生产反向代理后要 `trust proxy` 且分布式要用 Redis 存计数。

### 6.2 优雅退出

收到 SIGTERM/SIGINT → 先 `server.close()` 停掉新请求 → 等正在处理的请求完成 → 再退出。

```ts
const server = app.listen(port, () => { ... })

const shutdown = () => {
  server.close(() => process.exit(0))
}
```

## 9. 常见坑

1. supertest 用 `createApp()`，**不要**先 `app.listen()` 再测，否则测试会占端口、不结束
2. 测试之间数据串了 → 需要重置内存数据（beforeEach）
3. multer 超出大小抛 `MulterError`，errorHandler 不识别就变成 500
4. 文件名直接用用户原名 → 路径穿越风险，必须随机重命名
5. 安全中间件（helmet/cors/限流）尽量往前挂，日志中间件之后、路由之前
6. 部署时 `.env` 不提交；环境变量在平台后台配

## 10. 本周复盘问题（能答上来就过关）

- 单元测试和集成测试的区别？supertest 为什么不需要真的监听端口？
  单元测试：只测单个函数 / service，不启动服务器；集成测试：测 API 接口（起 app、发请求、查响应）。
  supertest 直接把请求发进 app 内部，不占端口、不用 listen、测完自动关——这得益于 createApp() 和 app.listen() 分离的组合根设计。
- mock 的作用？为什么 AI 应用开发特别依赖 mock？
  mock 的作用是替换 import 导入的东西，隔离外部依赖，让测试不依赖真实环境。
  AI 应用特别依赖 mock，因为如果不替换，测试会调用真实的 LLM API 接口，既耗费钱又不稳定（还有限流、延迟问题）。
- multer 的 diskStorage 和 memoryStorage 区别？各适合什么场景？
  diskStorage：把文件存在服务器磁盘上，落盘即持久化、重启不丢，适合需要长期保存的场景（本周用这个）。
  memoryStorage：把文件存在内存里（req.file.buffer），快、不占磁盘，但重启就丢、大文件会爆内存，适合"收到后立刻转给云存储 / LLM"的中转场景。
- 为什么上传文件不能直接存用户给的文件名？
  用户可控的文件名有安全隐患：路径穿越（如 ../../）、覆盖服务器文件、伪装恶意文件触发 XSS。
  所以用 randomBytes(16).toString('hex') 生成随机名，只保留扩展名，切断这几条攻击路径。
- helmet 解决了哪些攻击？CORS 白名单和限流分别防什么？
  1. helmet 解决：MIME 嗅探（X-Content-Type-Options: nosniff）、点击劫持（X-Frame-Options）、XSS（CSP 白名单兜底）、强制 HTTPS（HSTS）等。
  2. CORS 白名单：防止别的网站的浏览器跨域读取你的接口响应。注意 CORS 是浏览器拦截，不是服务器拒绝；防不了 curl/Postman，真正的门禁是 JWT 鉴权。
  3. 限流：防暴力破解（疯狂试密码）、防爬虫、防刷接口/DoS；超限返回 429。
- /healthz 的作用？优雅退出是怎么"优雅"的？
  /healthz 是健康检查接口，部署平台用它判断服务是否活着，返回 200 + { status: 'ok' }。
  优雅退出：收到 SIGTERM（部署平台发）或 SIGINT（Ctrl+C）→ 先 server.close() 停止接收新请求 → 等正在处理的请求完成 → 再 process.exit(0)。
  "优雅"就体现在：先停新请求、等旧请求处理完才退出，不直接 kill 导致请求断掉。
- 为什么生产不能用 tsx 直接跑？
  tsx 只是即时转译器，运行时才把 TS 翻译成 JS，不会生成文件、node 不能识别 TS；
  而且它不做类型检查、启动有转译开销、属于 devDependency。生产应该 pnpm build（tsc 编译到 dist/）再 node dist/index.js。
