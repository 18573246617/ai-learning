## 1. 为什么要写测试

手动测试的问题：改一处代码，不知道哪里坏了；接口越来越多，全靠 Postman 点一遍不现实。面试和真实团队里，"项目有没有测试、会不会写测试"是基本要求。

测试分三层：

| 层级 | 测什么 | 工具 |
|---|---|---|
| 单元测试 | 单个函数 / service（不启动服务器） | vitest |
| 集成测试 | API 接口（起 app、发请求、查响应） | vitest + supertest |
| 端到端 | 整个系统（数据库、外部依赖全真的） | 本周不做 |

本周做前两层，重点是**冒烟测试**：核心流程跑通——注册 → 登录 → 拿 token → 访问受保护接口。

## 2. vitest + supertest：给 API 写测试

### 2.1 安装

```bash
pnpm add -D vitest supertest @types/supertest
```

在 package.json 加脚本：`"test": "vitest run"`

### 2.2 为什么 supertest 不需要真的启动端口

```ts
request(createApp()).get('/tasks')
```

supertest 直接把请求发进 app 内部，**不占端口、不用 listen、测完自动关**。你 week2 把 `createApp()` 和 `app.listen()` 分开，正好就是为了这一刻——这就是"组合根"设计的好处。

### 2.3 第一个测试长什么样

```ts
import { describe, it, expect } from 'vitest'   // ① 从 vitest 导入测试三件套
import request from 'supertest'                 // ② 导入 supertest
import { createApp } from '../app'              // ③ 导入你的 app 工厂函数

describe('tasks 接口', () => {                  // ④ 分组
  it('GET /tasks 返回 200 和数组', async () => { // ⑤ 一条具体用例
    const res = await request(createApp()).get('/tasks')  // ⑥ 发起请求
    expect(res.status).toBe(200)                // ⑦ 断言 1
    expect(Array.isArray(res.body.data)).toBe(true)  // ⑦ 断言 2
  })
})
```

### 2.4 测试文件放哪

与被测代码同目录：`src/week2/router/tasks/index.test.ts`。运行：`pnpm test`。

### 练习 1

- 给 tasks 写 2 个测试：GET /tasks 返回 200 + 数组；POST /tasks 传非法 body（比如缺 title）返回 400
```ts
import { it, describe, expect } from 'vitest'
import request from 'supertest'
import { createApp } from '../../app'   // 测试文件与被测代码同目录（src/week2/router/tasks/index.test.ts）

// 测试进程不走 --env-file，必须手动设置 JWT_SECRET（否则登录签发 token 会失败）
process.env.JWT_SECRET = process.env.JWT_SECRET || 'test-jwt-secret'
const app = createApp()

// 注册 + 登录，动态拿 token（每个测试用随机用户名，避免内存数据串味）
const loginToken = async (username: string) => {
    await request(app).post('/auth/register').send({ username, password: '123456' })  // 必须 await！
    const res = await request(app).post('/auth/login').send({ username, password: '123456' })
    return res.body.data.token
}

describe('tasks 接口', () => {
    it('GET /tasks/list 返回 200 和数组', async () => {          // async + await 缺一不可
        const token = await loginToken(`tester_${Date.now()}`)
        const res = await request(app).get('/tasks/list')         // 第一个参数是 app，路径在方法里
            .set('Authorization', `Bearer ${token}`)
        expect(res.status).toBe(200)
        expect(res.body).toBeInstanceOf(Array)
    })

    it('POST /tasks/create 传非法 body 返回 400', async () => {
        const token = await loginToken(`tester_${Date.now()}`)
        const res = await request(app).post('/tasks/create')
            .set('Authorization', `Bearer ${token}`)
            .send({})                                            // 缺 title → zod 校验失败 → 400
        expect(res.status).toBe(400)
    })
})
```
- 给 auth 写 1 个完整流程测试：注册 → 登录拿到 token → 带 `Authorization: Bearer` 访问 /auth/getUserInfo 返回 200
```ts
import { it, describe, expect } from 'vitest'
import request from 'supertest'
import { createApp } from '../../app'   // src/week2/router/auth/index.test.ts

// 每个测试文件都要单独设置！（vitest 各文件环境独立，不会共享）
process.env.JWT_SECRET = process.env.JWT_SECRET || 'test-jwt-secret'
const app = createApp()

describe('auth完整测试流程', () => {
    it('注册 → 登录 → 带 token 访问 getUserInfo', async () => {
        const username = `user_${Date.now()}`                     // 动态用户名，先定义变量
        // ① 注册（必须 await，否则登录时用户还没建好）
        await request(app).post('/auth/register').send({ username, password: '123456' })
        // ② 登录拿 token（必须 await，token 在响应体里）
        const loginRes = await request(app).post('/auth/login').send({ username, password: '123456' })
        const token = loginRes.body.data.token
        // ③ 带 Bearer token 访问受保护接口
        const res = await request(app).get('/auth/getUserInfo')
            .set('Authorization', `Bearer ${token}`)
        expect(res.status).toBe(200)
        expect(res.body.data.userName).toBe(username)             // 返回的正是登录的用户
    })
})
```
### 2.5 关键坑：内存数据会串

你的数据是模块里的内存数组，多个测试跑下来数据会互相污染（第一个测试注册的用户，第二个测试还能看到）。解决思路：

- 导出一个 `reset()` 之类的函数，`beforeEach` 里清空数据
- 这暴露了一个设计问题：**数据层要"可重置、可注入"**，第 6 周重构 repository 时会彻底解决

## 3. mock 外部请求（为 AI 应用打基础）

为什么 AI 应用开发**特别依赖 mock**：LLM API 贵、慢、有频率限制，测试不可能真调。等你做 RAG 和 Agent 时，所有外部调用都要 mock 掉。

基本用法：

```ts
import { vi } from 'vitest'

const mockFetch = vi.fn().mockResolvedValue({
  ok: true,
  json: async () => ({ choices: [{ text: '你好' }] }),
})
```

`vi.fn()` 造一个假函数，断言它**被调用过、参数对、返回预期结构**；`vi.mock()` 可以替换整个模块。

### 练习 2

写一个"调用外部天气 API"的函数（用 fetch 或你熟悉的库），再写测试：

- 用 `vi.fn()` mock 掉网络调用，断言函数被调用且返回你预设的结构
- 模拟"网络失败"，断言函数能处理错误而不是抛出去

## 4. multer 文件上传

### 4.1 安装

```bash
pnpm add multer
pnpm add -D @types/multer
```

### 4.2 核心概念

- `upload.single('file')`：解析 multipart 表单，把文件挂到 `req.file`
- 两种存储：
  - `diskStorage`：存到服务器磁盘（本周用这个）
  - `memoryStorage`：存内存，适合后面直接传给云存储或 LLM（阶段三常用）
- 大小限制：`limits: { fileSize: 2 * 1024 * 1024 }`
- 类型限制：`fileFilter` 回调里检查 `file.mimetype`

### 4.3 生产要点（重点，面试爱问）

1. **不能信任文件名**：用户传 `../../etc/passwd` 这种名字会路径穿越。必须用 `randomBytes` 生成新文件名
2. **限制大小和类型**：`limits` + `fileFilter` 双保险
3. **MulterError 要识别**：超大小会抛 `MulterError`，你的 errorHandler 不识别它就会返回 500，要单独处理成 400/413
4. **上传目录独立**：存到 `uploads/`，并加进 `.gitignore`

### 练习 3

建一个 `POST /upload` 接口：

- 只收图片（jpg / png），最大 2MB
- 文件保存到 `uploads/` 目录，**文件名用随机数生成，不保留用户原名**
- 用 Postman 传一张图片验证成功；传一个 .txt 验证被拒（返回 4xx 而不是 500）

## 5. 安全加固：helmet / CORS / 限流

### 5.1 helmet：一行加安全头

```ts
import helmet from 'helmet'
app.use(helmet())
```

自动加 `X-Content-Type-Options`（防 MIME 嗅探）、`X-Frame-Options`（防点击劫持）、HSTS 等。面试能说出 2-3 个它设置的头就算过关。

### 5.2 CORS：白名单

```bash
pnpm add cors
pnpm add -D @types/cors
```

开发环境可以放开，生产只允许你的前端域名。**白名单从环境变量读**（如 `CORS_ORIGINS`），符合 12-Factor。

### 5.3 限流：防暴力破解

```bash
pnpm add express-rate-limit
```

- 全局限流：所有接口一个基础额度
- 登录接口单独更严：比如 1 分钟最多 10 次，超过返回 **429**
- 理由：暴力破解密码、爬虫、刷接口

### 练习 4

- 在 app.ts 挂上 helmet + cors（白名单从 env 读）+ 全局限流
- 登录接口单独限流：1 分钟最多 10 次，超过返回 429
- 用 Postman 连续请求验证 429

## 6. 健康检查 + 优雅退出

### 6.1 /healthz

部署平台用它判断"服务活着吗"。返回 200 + `{ status: 'ok' }`。

注意区分：

- **存活检查**：只查进程活着（本周做这个）
- **就绪检查**：还查数据库等外部依赖通不通（阶段二接数据库后升级）

### 6.2 优雅退出

收到 SIGTERM/SIGINT → 先 `server.close()` 停掉新请求 → 等正在处理的请求完成 → 再退出。

```ts
const server = app.listen(port, () => { ... })

const shutdown = () => {
  server.close(() => process.exit(0))
}
process.on('SIGTERM', shutdown)
process.on('SIGINT', shutdown)
```

为什么生产需要：部署平台滚动更新时，旧实例要"体面退场"，不能直接 kill 导致正在处理的请求断掉。

- 在 index.ts 加优雅退出代码

## 9. 常见坑

1. supertest 用 `createApp()`，**不要**先 `app.listen()` 再测，否则测试会占端口、不结束
2. 测试之间数据串了 → 需要重置内存数据（beforeEach）
3. multer 超出大小抛 `MulterError`，errorHandler 不识别就变成 500
4. 文件名直接用用户原名 → 路径穿越风险，必须随机重命名
5. 安全中间件（helmet/cors/限流）尽量往前挂，日志中间件之后、路由之前
6. 部署时 `.env` 不提交；环境变量在平台后台配
