## 1. 为什么 sha256 存密码不够（升级动机）

你现在的做法：`sha256(密码)` 直接存。

两个致命问题：

1. **相同密码 → 相同哈希**：100 个用户都用 "123456"，库里就有 100 个一模一样的哈希，攻击者一眼就能看出来
2. **sha256 太快 + 无盐**：攻击者可以提前算好常见密码的哈希表（彩虹表），拿到库直接比对，秒破

### bcrypt 怎么解决

- **自动加盐**：每个密码哈希时自动生成随机盐，"123456" 存两次得到两个完全不同的哈希
- **故意慢**：bcrypt 设计上就是慢哈希，攻击者暴力破解的成本指数级上升
- 验证时不需要你管盐：`bcrypt.compare(明文, 哈希)` 内部会自动提取盐重新计算

```ts
import bcrypt from 'bcrypt'

// 注册：哈希后存储（10 是"工作因子"，越大越慢越安全，10 是常用值）
const hash = await bcrypt.hash('123456', 10)

// 登录：明文和库里哈希比对，返回 true/false
const ok = await bcrypt.compare('123456', hash)
```

### 练习 1

- 安装 `bcrypt`，把注册里的 `sha256` 换成 `bcrypt.hash`，登录里的比对换成 `bcrypt.compare`
- 注册两个相同密码的用户，观察库里两个哈希**不一样**（这是 sha256 做不到的）
- 用 `bcrypt.hash('123456', 10)` 感受一下它比 sha256 慢多少（慢是特性，不是 bug）

## 2. JWT：签发与校验

### 2.1 为什么换 JWT

你现在的 token（randomBytes）有两个问题：

1. **永不过期**——一旦泄露，攻击者永远能用
2. **要查库**——每个请求都要去数据库里找 token

JWT 是**自包含**的：token 里本身就写着"谁 + 什么时候过期"，服务器校验时**不需要查库**，只验证签名和过期时间。

### 2.2 JWT 长什么样

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VybmFtZSI6ImphbWVzIiwiZXhwIjoxNz... .签名
```

三段：`header.payload.signature`

- header：算法信息
- payload：你放的数据（username、exp 过期时间）
- signature：用密钥对前两段签名，防止篡改

### 2.3 签发和校验

```ts
import jwt from 'jsonwebtoken'

// 签发：payload + 密钥 + 过期时间
const token = jwt.sign({ username: 'james' }, SECRET, { expiresIn: '7d' })

// 校验：成功返回 payload，失败（过期/被篡改）抛异常
const payload = jwt.verify(token, SECRET)   // { username: 'james', iat, exp }
```

**关键：SECRET 必须放环境变量**（`process.env.JWT_SECRET`），用 week3 学的 `--env-file` 加载，绝不能写死在代码里。

### 2.4 改造点

- login 成功：不再 `randomBytes`，改成 `jwt.sign` 返回
- checkAuth：不再查库比对 token，改成 `jwt.verify`，成功就把 payload 挂到 `req.user`
- 过期 token 校验失败 → 401（jwt.verify 抛 TokenExpiredError，包 try/catch）

## 3. Authorization: Bearer 规范

你现在用的是自定义请求头 `x-http-token`。行业标准写法是：

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

前端：

```js
headers: { Authorization: `Bearer ${token}` }
```

后端取的时候要去掉前缀：

```ts
const header = req.headers.authorization          // "Bearer xxxx"
const token = header?.startsWith('Bearer ') ? header.slice(7) : undefined
```

> 注意：`Bearer` 的 B 是大写，`Bearer ` 后面有个空格。

把 `checkAuth` 改成从 `Authorization: Bearer` 取 token。

## 4. localStorage vs cookie（前端存哪）

这是概念题 + 面试题，本周能说清取舍就行，不用写代码。

| | localStorage | cookie（HttpOnly） |
|---|---|---|
| 谁能读到 | 任何 JS 都能读 | JS 读不到，只有浏览器自动带上 |
| 主要风险 | **XSS 攻击**能偷 token | **CSRF 攻击**（cookie 会自动带） |
| 防 XSS | 靠你写代码小心 | 天然免疫 |
| 防 CSRF | 天然免疫（要手动加 header） | 需要 SameSite / CSRF token |
| 适用场景 | 纯前端项目、API 服务 | 传统 Web、同源部署 |

一句话结论：**简单项目用 localStorage + 注意 XSS；要极致安全用 HttpOnly cookie + SameSite。** AI 应用（对接 API 服务）常见做法是 localStorage。

## 5. pino：结构化日志

### 5.1 为什么不用 console.log

`console.log('登录成功', user)` 的输出是一行文本，人看着还行，但**日志系统没法解析**（没法按字段搜索、统计、告警）。

### 5.2 pino 输出 JSON 行

```ts
import pino from 'pino'

const logger = pino()

logger.info({ userId: 1, username: 'james' }, '登录成功')
// 输出：{"level":30,"time":...,"msg":"登录成功","userId":1,"username":"james"}
```

每个字段都能被日志系统索引、过滤、告警。

### 5.3 改造点

- app.ts 里换成 pino 写请求日志（或和现有 logger 并存对比一下）
- auth 路由里加 `logger.info({ username }, '登录成功')`、`logger.warn('登录失败')`
- 错误处理中间件里用 `logger.error(err)` 替代 `console.error`

## 7. 常见坑

1. `JWT_SECRET` 写死在代码里 → 必须放 `.env`（用 week3 的 `--env-file`）
2. `jwt.verify` 失败会抛异常（过期、篡改）→ 必须 try/catch，返回 401，不能让它变成 500
3. bcrypt 很慢是特性不是 bug——每个请求都 `bcrypt.hash` 会拖慢服务，注册时才 hash，登录只用 `compare`
4. `Bearer` 的 B 大写、后面有空格，取的时候别写错
5. token 存 localStorage 要意识到 XSS 风险（别用 `innerHTML` 渲染用户输入）
