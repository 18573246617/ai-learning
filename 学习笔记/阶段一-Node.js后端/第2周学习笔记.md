## 1. 为什么需要框架

第 1 周用原生 http 写路由，靠 if/else 判断 url 和 method，接口一多就乱。Express 把"收到请求 → 找路由 → 返回响应"这件事封装好了：

- 路由：`app.get("/tasks", handler)` 一行一个接口
- 中间件：日志、JSON 解析等公共逻辑抽出来复用
- 参数解析：路径参数、查询参数、请求体自动帮我们取

框架只是工具，第 1 周学的"服务器本质"（收到请求、返回响应、状态码、响应头）依然是理解一切的底座。

## 3. 路由：增删改查

HTTP 方法 + 路径 = 一个接口：

| 方法 | 路径 | 作用 | 成功状态码 |
|---|---|---|---|
| GET | /tasks | 查列表 | 200 |
| GET | /tasks/:id | 查单个 | 200 |
| POST | /tasks | 创建 | 201 |
| PUT | /tasks/:id | 更新 | 200 |
| DELETE | /tasks/:id | 删除 | 204 |

```ts
import { Router } from "express"

export const tasksRouter = Router()

// 路径参数：req.params.id（注意：永远都是字符串！）
tasksRouter.get("/:id", (req, res) => {
  res.json({ id: req.params.id })
})

// 查询参数：?completed=true&keyword=xx
tasksRouter.get("/", (req, res) => {
  res.json(req.query)
})
```

三个取值位置的记忆：`req.params`（路径里的）、`req.query`（? 后面的）、`req.body`（请求体，需要 `express.json()` 才有）。

## 4. 中间件机制

中间件是"请求流水线"上的一个个工位：请求进来，按注册顺序经过每个中间件，每个中间件可以处理、修改请求，然后调用 `next()` 放行给下一个。

```ts
// 自定义日志中间件
export function requestLogger(req, _res, next) {
  console.log(`${new Date().toISOString()}  ${req.method}  ${req.originalUrl}`)
  next()
}
```

两个常用的内置中间件：

- `express.json()`：解析 JSON 请求体，结果放到 `req.body`
- `express.static()`（第 3 周以后会用到）：托管静态文件

顺序很重要：

1. 日志、JSON 解析要放在业务路由**之前**
2. 404 兜底要放在所有路由**之后**

## 5. async/await + 错误处理

为什么路由要写 async？因为后面接数据库（Prisma）、调 AI 接口都是异步的。现在数据层故意写成 async，提前养成习惯。

每个 async 路由的固定套路：

```ts
tasksRouter.get("/:id", async (req, res, next) => {
  try {
    const task = await findTask(Number(req.params.id))
    if (!task) {
      res.status(404).json({ error: "任务不存在" })
      return
    }
    res.json(task)
  } catch (err) {
    next(err)   // 交给错误处理中间件
  }
})
```

错误处理中间件的特殊之处：**必须有 4 个参数**（err, req, res, next），Express 靠参数个数识别它：

```ts
export function errorHandler(err, _req, res, _next) {
  console.error("出错了:", err)
  res.status(500).json({ error: "服务器内部错误" })
}
```

> 补充：Express 5 会自动捕获 async 路由里抛出的错误并交给错误中间件，即使不写 try/catch 也能兜住。但我们还是显式写 try/catch，一是更清楚，二是兼容老代码。

## 6. zod 参数校验

原则：**永远不要信任输入**。前端可能传空标题、错误类型、超长字符串，后端必须自己校验。

zod 写法：先定义规则，再用 `safeParse` 校验：

```ts
一、定义类型的方法（z. 开头）
| 方法 | 作用 | 例子 |
|---|---|---|
| `z.string()` | 字符串 | `z.string()` |
| `z.number()` | 数字 | `z.number()` |
| `z.boolean()` | 布尔 | `z.boolean()` |
| `z.enum([...])` | 只能取列表里的值 | `z.enum(["low", "medium", "high"])` |
| `z.array(...)` | 数组 | `z.array(z.string())` |
| `z.object({...})` | 对象（请求体最常用） | `z.object({ title: z.string() })` |
| `z.union([...])` | 多个类型二选一 | `z.union([z.string(), z.number()])` |

二、加规则的方法（跟在类型后面 . 出来的）
| 方法 | 作用 | 例子 |
|---|---|---|
| `.min(n)` | 至少 n 个字符/最小值 | `z.string().min(1)` |
| `.max(n)` | 最多 n 个字符/最大值 | `z.string().max(100)` |
| `.trim()` | 去首尾空格 | `z.string().trim()` |
| `.email()` | 必须是邮箱格式 | `z.string().email()` |
| `.url()` | 必须是网址格式 | `z.string().url()` |
| `.regex(/.../)` | 匹配正则 | `z.string().regex(/^\d+$/)` |
| `.int()` | 必须是整数 | `z.number().int()` |
| `.positive()` | 必须是正数 | `z.number().positive()` |
| `.optional()` | 可以不传 | `z.string().optional()` |
| `.default(x)` | 不传就用默认值 | `z.enum([...]).default("medium")` |
| `.refine(fn)` | 自定义规则 | `z.object({...}).refine(...)` |
| `.transform(fn)` | 校验后转换数据 | `z.enum(["true","false"]).transform(v => v === "true")` |

三、执行校验的方法（对 schema 调用）
| 方法 | 作用 |
|---|---|
| `.parse(data)` | 校验，失败**抛异常**（路由里不用） |
| `.safeParse(data)` | 校验，失败**不抛**，返回结果对象（路由里用这个） |

四、两个最常用的工具
z.coerce.number()：强制转换——把字符串 "1" 变成数字 1（解决 req.params.id 是字符串的问题）
result.error.flatten()：把错误整理成好看的结构，方便返回给前端

import { z } from "zod"

// 校验规则
const createTaskSchema = z.object({
  title: z.string().min(1, "标题不能为空").max(100, "标题最长 100 个字"),
  priority: z.enum(["low", "medium", "high"]).default("medium"),
})



// 使用
const result = createTaskSchema.safeParse(req.body)
if (!result.success) {
  res.status(400).json({ error: "请求体不合法", details: result.error.flatten() })
  return
}
// 通过校验后，result.data 才是安全可靠的数据
```

三个校验位置：

- body：`z.object({...})`
- 路径参数：`z.coerce.number()`（把字符串转数字）
- query：`z.enum(["true","false"]).transform(...)`（字符串转布尔）

校验失败返回 400，details 里是每个字段的具体错误。

## 9. 常见坑

1. `req.body` 是 undefined → 忘了在路由之前加 `app.use(express.json())`
2. `req.params.id` 是字符串，直接拿去做比较会踩坑 → 用 `z.coerce.number()` 转数字
3. 中间件顺序：JSON 解析必须在路由前；404 兜底必须在最后
4. `res.status(204).end()` 后面不要再 `res.json`，一个请求只能有一个响应
5. PUT 与 PATCH：严格说 PUT 是全量替换、PATCH 是部分更新。我们简化用 PUT 做部分更新，面试时能说清区别就行
6. zod 校验失败后必须 `return`，否则代码会继续往下执行

## 10. 本周复盘问题（能答上来就过关）

- 中间件是什么？为什么注册顺序重要？
   中间键是处理请求中的‘插件’，中间件按注册顺序从上到下执行，所以解析请求体的中间件必须放在读 body 的路由之前，404 兜底必须放在所有路由之后——顺序错了，功能就错。
- `express.json()` 做了什么？不加会怎样？ 
   处理客户端发过来的请求参数，把他转化为json格式，并且设置 请求头content-typoe:'application/json'

- `req.params`、`req.query`、`req.body` 分别装什么？
`req.params`：路径后面的参数，例如 /task/1
`req.query`:路径？后面的参数 ，例如/task/1?name=james
`req.body`:post请求体的数据

- 为什么错误处理中间件必须 4 个参数？
 Express 靠参数个数来识别"这是错误处理中间件"——只有正好 4 个参数 (err, req, res, next) 的中间件，Express 才会把错误传给它的第一个参数 err。你写 3 个参数，Express 就当它是普通中间件，错误根本到不了它手里
   因为要捕获错误信息
- zod 的 `safeParse` 和 `parse` 有什么区别？
是否会自动抛出异常，且阻断程序运行
- 数据层为什么要和接口层分开？
使得代码更加清晰，不容易乱
将来换数据库时，只改数据层，路由一行不用动
