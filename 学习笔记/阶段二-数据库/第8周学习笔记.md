## 1. 本周全景：关系才是数据库的核心

第 7 周你玩的是单表。真实业务几乎全是关系：一个用户有多个任务，一个任务可以有多个标签。新手最容易犯的错是"一张大表全装下"：

| 一张大表（反例） | 问题 |
|---|---|
| tasks 表里存 `username`、`user_email`、`tag1`、`tag2`、`tag3` | 用户改邮箱要改他所有任务行（**更新异常**） |
| 一个新用户没任务，就没法存进 tasks 表（**插入异常**） | 或者得塞一堆 NULL |
| 删掉最后一个任务，用户信息跟着消失（**删除异常**） | 数据被意外带走 |

正确做法：**把数据拆到各自该在的表，用外键连起来，查询时用 JOIN 拼回来**。本周四件事正好是一条完整链路：

```text
设计关系（ER 图） → 建表（外键 / 中间表） → 查询（JOIN / 聚合） → 性能（索引 / EXPLAIN）
```

面试里"数据库"部分问得最多的就是 JOIN 和索引，这两块本周都摸到了。

## 2. 三种关系（背下来）

判断方法：**读句子，看是"一个对一个""一个对多个"，还是"多个对多个"**。

### 2.1 一对多（最常见）

例子：一个用户有多个任务，一个任务只属于一个用户。

**外键永远放在"多"的那一边**——tasks 表放 `user_id`。反过来（users 表存 `task_ids` 数组）是反模式，查询和约束都会失控。

```sql
CREATE TABLE tasks (
    id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title   TEXT   NOT NULL
);
```

### 2.2 一对一

例子：用户和"用户资料"（昵称、头像、签名）。拆开的理由通常是：资料是可选的、敏感的、或者很少查。

做法：子表用**同一个 id 当主键兼外键**（共享主键），天然保证"一个用户最多一条资料"。

```sql
CREATE TABLE user_profiles (
    user_id    BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    nickname   VARCHAR(50),
    bio        TEXT,
    avatar_url TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

也可以写成 `user_id BIGINT NOT NULL UNIQUE REFERENCES users(id)`——加 UNIQUE 就等于一对一。

### 2.3 多对多（必须用中间表）

例子：一个任务可以有多个标签，一个标签可以贴到多个任务上。

两边都不能放外键（任务表存 tag_ids、标签表存 task_ids 这种数组，约束和外键统统失效）。正确做法是新建一张**中间表**，只存"谁连谁"：

```sql
CREATE TABLE task_tags (
    task_id BIGINT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    tag_id  BIGINT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (task_id, tag_id)
);
```

中间表的复合主键 `(task_id, tag_id)` 一箭双雕：一是主键，二是**防止重复打同一个标签**。

### 2.4 小结

| 关系 | 例子 | 外键放哪 | 关键约束 |
|---|---|---|---|
| 一对一 1:1 | users ↔ user_profiles | 子表拿用户的 id | 子表外键加 PRIMARY KEY 或 UNIQUE |
| 一对多 1:N | users → tasks | **多**的一方（tasks.user_id） | NOT NULL + REFERENCES |
| 多对多 M:N | tasks ↔ tags | 单独一张中间表 | 中间表复合主键 + 两个外键 |

## 5. JOIN：把拆开的数据拼回来（练习 3，本周重点）

JOIN 的本质：**按关联列把两张表"并排拼"**，不是把子表塞进父表。拼的规则由 `ON` 决定。

### 5.1 INNER JOIN vs LEFT JOIN

| 类型 | 结果 | 什么时候用 |
|---|---|---|
| `INNER JOIN` | 只保留两边都能配上的行 | "列出有任务的用户和他们的任务" |
| `LEFT JOIN` | 保留左表全部，右表配不上补 NULL | "列出所有用户，有任务就显示" |

判断口诀：**问"主体是谁、要不要保留没配上的"**。要保留没配上的（比如"没有任务的用户也要列出来"）就用 LEFT。

```sql
-- 只列有任务的用户（配不上的直接不要）
SELECT u.username, t.title, t.completed
FROM users AS u
INNER JOIN tasks AS t ON t.user_id = u.id
ORDER BY u.id, t.id;

-- 所有用户都列出来，没任务的 title 显示 NULL
SELECT u.username, t.title
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id
ORDER BY u.id, t.id;
```

### 5.2 多对多要连两次

想查"任务 + 它的标签 + 所属用户"，要沿着中间表连过去（一次 JOIN 一张表）：

```sql
SELECT u.username, t.title, tg.name AS tag
FROM tasks AS t
INNER JOIN users     AS u  ON u.id = t.user_id
INNER JOIN task_tags AS tt ON tt.task_id = t.id
INNER JOIN tags      AS tg ON tg.id = tt.tag_id
ORDER BY u.username, t.id, tg.name;
```

### 5.3 三个必踩的坑（提前记住）

**坑 1：JOIN 之后行数会变多。** 一个用户有 10 个任务，`users JOIN tasks` 后这个用户就出现 10 行——这是正常的"展开"。所以 JOIN 完再 `count(*)` 数出来的不是用户数，想数用户要用 `COUNT(DISTINCT u.id)`。

**坑 2：LEFT JOIN 的过滤条件写错位置会退化成 INNER。**

```sql
-- 正确：条件写在 ON 里，「没任务的用户」仍然保留
SELECT u.username, t.title
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id AND t.completed = FALSE;

-- 错误：条件写在 WHERE 里，NULL 行被过滤掉，等于 INNER JOIN
SELECT u.username, t.title
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id
WHERE t.completed = FALSE;
```

规则：**想过滤"右表"又要保留左表全部行，条件就写在 ON 里**。

**坑 3：忘了 ON 或连错列 = 笛卡尔积。** 两张表 100 行 × 100 行 = 10000 行，查询突然变慢就先查这里。

### 5.4 反连接：查"没有 X 的 Y"

"找出一个任务都没有的用户"——用 LEFT JOIN + IS NULL：

```sql
SELECT u.username
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id
WHERE t.id IS NULL;
```

## 6. 聚合：COUNT、GROUP BY、HAVING（练习 4）

聚合 = 把多行"压成"一行统计值。数据库把一堆行切成一组组，每组算一个结果。

### 6.1 COUNT 的三种写法（高频面试题）

| 写法 | 含义 | 注意 |
|---|---|---|
| `COUNT(*)` | 数行数，包含 NULL 行 | LEFT JOIN 里会把"补 NULL 的行"也算上 |
| `COUNT(列)` | 数该列**非 NULL** 的行 | LEFT JOIN 数右表行数必须用这个 |
| `COUNT(DISTINCT 列)` | 数不重复的值 | 数"有多少个用户"用这个 |

经典场景：数每个用户的任务数（包括没任务的用户）：

```sql
SELECT u.username, COUNT(t.id) AS task_count
FROM users AS u
LEFT JOIN tasks AS t ON t.user_id = u.id
GROUP BY u.id, u.username
ORDER BY task_count DESC;
```

写成 `COUNT(*)` 就错了——没任务的用户会被数成 1。

### 6.2 GROUP BY 的规则

`SELECT` 里出现的列，**要么在 GROUP BY 里，要么包在聚合函数里**。原因是分组后每组的普通列有多个值，数据库不知道该显示哪一个。

### 6.3 WHERE 和 HAVING 的区别

执行顺序要背下来：

```text
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

| | 作用时机 | 能不能用聚合函数 |
|---|---|---|
| `WHERE` | 分组**前**过滤行 | 不能（此时还没分组） |
| `HAVING` | 分组**后**过滤组 | 能 |

```sql
-- 任务数 >= 2 的用户
SELECT u.username, COUNT(t.id) AS task_count
FROM users AS u
JOIN tasks AS t ON t.user_id = u.id
GROUP BY u.id, u.username
HAVING COUNT(t.id) >= 2;
```

## 7. 索引与 EXPLAIN（练习 5）

### 7.1 索引是什么

索引 = 书的目录。没有它，数据库只能一页页翻（全表扫描）；有它就能直接跳到目标位置。PG 默认用 B-tree 索引，适合等值查找和范围查询。

### 7.2 什么时候建，什么时候不建

| 建 | 不建 |
|---|---|
| 频繁出现在 `WHERE` 的列 | 表很小（几行，扫全表也快） |
| `JOIN ON` 的关联列（**尤其外键列**） | 写多读少的表（每次写都要维护索引） |
| 需要 `ORDER BY` 排序的列 | 区分度低的列（比如性别、布尔值单独建没意义） |
| 唯一约束场景 | 已经被复合索引的"最左列"覆盖 |

**最容易忽略的一条：PostgreSQL 不会自动给外键列建索引。** 主键和 UNIQUE 会自动建，外键不会。所以 `tasks(user_id)`、`task_tags(tag_id)` 都要手动建——不然删除一个用户时，数据库要全表扫 tasks 才能找到他的任务。

```sql
CREATE INDEX idx_tasks_user_id       ON tasks(user_id);
CREATE INDEX idx_task_tags_tag_id    ON task_tags(tag_id);
```

注意 `task_tags` 的复合主键 `(task_id, tag_id)` 只自动建了以 `task_id` 开头的索引，按 `tag_id` 反向查（"这个标签用在哪些任务上"）需要上面那条单独的索引。这就是**复合索引最左前缀**：`(a, b)` 支持 `a`、`a+b`，不支持单独 `b`。

### 7.3 EXPLAIN 怎么读（看懂即可，不用会调优）

```sql
EXPLAIN SELECT * FROM tasks WHERE user_id = 1;
EXPLAIN ANALYZE SELECT * FROM tasks WHERE user_id = 1;   -- 会真正执行，带实际耗时
```

重点看两件事：

- `Seq Scan`（全表扫描）vs `Index Scan`（走索引）：加了索引后能不能变过来
- `cost` 和 `rows`：优化器估算的代价和行数；`EXPLAIN ANALYZE` 里还有 `actual time` 真实耗时
