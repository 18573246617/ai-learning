## 1. 本周全景：一次"取数据"里藏着四个决策

写完第 9 周你会发现，`findUnique`、`create` 这类单表操作没什么决策空间——照着类型填就行。真实业务里查询一复杂，就立刻冒出四个必须自己拍的决定：

| 决策 | 第 8 周手写 SQL 时你怎么做的 | 本周 Prisma 的对应物 |
|---|---|---|
| 关联数据要不要一起取？取多少层？ | 写 JOIN 还是分两条查询 | `include` / `select` 嵌套 |
| 条件写在主表还是关联表？ | `WHERE` vs `ON` vs `NOT EXISTS` | `some` / `every` / `none` |
| 一次请求要写多张表，失败怎么办？ | `BEGIN ... COMMIT / ROLLBACK` | `$transaction` |
| 列表怎么翻页？深翻会不会慢？ | `LIMIT / OFFSET` vs `WHERE id > ?` | `skip/take` vs `cursor` |

**这四件事的顺序不是随便排的**：前两个决定"查得对不对"，后两个决定"查得省不省、写得稳不稳"。面试问"你用过 Prisma 吗"，深入下去问的一定是这四个。

对照表（把第 8 周的手写功夫接上）：

| 第 8 周 SQL | 第 10 周 Prisma |
|---|---|
| `tasks LEFT JOIN task_tags LEFT JOIN tags` | `include: { taskTags: { include: { tag: true } } }` |
| `NOT EXISTS (SELECT 1 FROM tasks ...)` | `where: { tasks: { none: {} } }` |
| `GROUP BY users.id` + `COUNT(t.id)` | `_count: { select: { tasks: true } }` |
| `LIMIT 10 OFFSET 20` | `skip: 20, take: 10` |
| `WHERE id < 100 ORDER BY id DESC LIMIT 10` | `cursor: { id: 100 }, skip: 1, take: 10` |
| `BEGIN; ...; COMMIT;` | `prisma.$transaction(...)` |

## 2. 关系查询：include / select 嵌套 / 关系过滤（练习 1）

### 2.1 三个层级，别混

第 9 周你只碰了第一个层级。本周要往上走：

```ts
// 层级 1：单表，只有标量字段
prisma.tasks.findMany()

// 层级 2：带一层关联（一对多 / 多对一）
prisma.users.findMany({ include: { tasks: true } })

// 层级 3：多对多要连两次——先到中间表，再到标签
prisma.tasks.findMany({
  include: { taskTags: { include: { tag: true } } },
})
```

`include` 里可以继续 `include` / `select`，这是 Prisma 最有表达力的地方。第 8 周你手写了三表 JOIN，这里两行就出来了——但**你要能说出它生成的 SQL 长什么样**，这是本周的隐性要求。

### 2.2 `include` 和 `select` 不是一回事

| | 语义 | 结果 |
|---|---|---|
| `select` | 白名单：**只要**这几列 | 没列的字段，TS 类型里就没有 |
| `include` | 默认全要，**再加上**这些关系 | 标量字段全在 |

两个规则要记牢：

1. **同一层级不能同时写 `select` 和 `include`**，类型直接报错。要混用就往下嵌套：`select: { id: true, title: true, taskTags: { select: { tag: true } } }`。
2. `select` 是安全边界。第 9 周你在 service 里用解构剔 `passwordHash`，那是补救；**更稳的做法是在查询处就用 `select` 根本不让它出来**。本周"我的任务"要返回用户信息时，把这条用上。

### 2.3 聚合的 Prisma 版：`_count`

第 8 周的 `GROUP BY` + `COUNT` 在这里变成：

```ts
prisma.users.findMany({
  select: { username: true, _count: { select: { tasks: true } } },
})
```

注意它只给**数量**，不给分组明细。要"每个用户已完成 / 未完成各多少"这种条件聚合，`_count` 就不够用了，得回 `groupBy`：

```ts
prisma.tasks.groupBy({ by: ['userId', 'completed'], _count: true })
```

`groupBy` 是 Prisma 里离 SQL 最近的方法，写完记得想想第 8 周"WHERE 和 HAVING 执行顺序"那张图——`groupBy` 的 `having` 参数就是 HAVING。

### 2.4 关系过滤：`some` / `every` / `none`

这是本周最容易被低估的三个词。它们把"条件"从主表挪到了关联表上：

| 写法 | 含义 | 第 8 周对应 |
|---|---|---|
| `tasks: { some: { completed: false } }` | 存在至少一条满足的任务 | `EXISTS` / `INNER JOIN` 去重 |
| `tasks: { every: { completed: true } }` | 所有任务都满足（**零任务也算 true**） | 没有直接对应，最容易理解错 |
| `tasks: { none: {} }` | 一条都没有 | `NOT EXISTS`（反连接） |

两个坑，提前说：

- `every` 在"关联表为空"时返回 `true`——逻辑上的空真。查"所有任务都完成的用户"时，charlie（零任务）会混进来。要排除就加 `tasks: { some: {} }`。
- `some: {}` 空对象 = "至少有一条"，正好用来写 `tasks: { none: {} }` 的反面。

对**一对一**关系，没有 some/every/none，用的是 `is` / `isNot`（本周用不到，记住有这回事就行）。

## 3. 嵌套写入：一次请求写多张表（练习 2）

### 3.1 `create` 里能嵌套什么

你的 `seed.ts` 里已经用过一次了（`taskTags: { create: [...] }`），本周要成体系地掌握四种：

| 嵌套操作 | 作用 | 典型场景 |
|---|---|---|
| `create` | 新建关联行 | 新建任务同时建标签关联 |
| `connect` | 连到**已存在**的行（按唯一字段） | 给任务挂已有标签 |
| `connectOrCreate` | 存在就连接，不存在就建 | "打标签"接口：标签是用户输入的，可能新可能旧 |
| `createMany` | 批量建（注意：只有一层，不支持嵌套） | 批量导入 |

`connectOrCreate` 是本周的高频点，写法固定：

```ts
taskTags: {
  create: tagNames.map((name) => ({
    tag: { connectOrCreate: { where: { name }, create: { name } } },
  })),
}
```

**它为什么必须存在**：如果只用 `connect`，用户输入了一个新标签名，Prisma 报 `P2025`（记录不存在）——这就是第 9 周学的错误码在实际业务里的落点。

### 3.2 嵌套更新：五个动作

```ts
data: {
  taskTags: {
    create: [...],      // 加关联
    deleteMany: {...},  // 删符合条件的关联
    set: [...],         // 整体替换（"重新打标签"最常用）
  },
}
```

`set` 是"把关联改成恰好这些"——不用自己算差集，Prisma 会删掉多的、补上少的。打标签场景里 `set` 比 `deleteMany + create` 干净。

### 3.3 什么时候**不要**用嵌套写

嵌套写很爽，但它有一个硬伤：**所有动作都在一条 `INSERT ... RETURNING` / 一条 `UPDATE` 语句的语义里，你没法在中间插入判断**。

需要"先查再决定"的时候（比如"标签不存在就报错，不要自动建"），嵌套写表达不了，这时要么两次调用包事务，要么退化成显式 `$transaction`。判断标准很简单：

> 一次写里的每个动作都**不依赖前面动作的结果** → 嵌套写；有依赖 → 事务。

## 4. 分页：skip/take 与游标（练习 3，本周重点）

### 4.1 offset 分页：先写对，再想快

```ts
prisma.tasks.findMany({
  where: { userId },
  orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
  skip: (page - 1) * pageSize,
  take: pageSize,
})
```

`orderBy` 一定要带 `id` 兜底——第 8 周你自己在 `04-select-queries.sql` 里答过"同一秒创建的顺序不稳定"，那是同一个问题，只是从 SQL 搬到了 Prisma。

### 4.2 深分页为什么慢（用第 8 周的 EXPLAIN 解释）

`OFFSET 100000` 你不是"跳过 10 万行"这么简单，数据库要**真的把前 10 万行读出来再丢掉**。所以第 10001 页和第一页的耗时差几个数量级。这和第 8 周"小表不走索引"是同一类观察：不是语法问题，是执行计划问题。

> 加分练习里会让你造 10 万行数据，用 `EXPLAIN ANALYZE` 亲眼看到 `Index Scan` 也要扫 10 万行——那个瞬间比看十篇文章都管用。

### 4.3 游标分页：用"上一页最后一条"当锚点

```ts
prisma.tasks.findMany({
  where: { userId },
  orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
  cursor: { id: lastId },   // 上一页最后一条的唯一键
  skip: 1,                  // 跳过 cursor 指向的那条本身
  take: pageSize,
})
```

- `cursor` **必须是唯一字段**（和 `findUnique` 的 where 同理）。复合排序的场景，cursor 要么用单唯一键，要么用 Prisma 的复合唯一键。
- `skip: 1` 最容易忘。忘了的结果是**每页重复一条**——上一页的最后一条永远出现在下一页第一条。这个 bug 很隐蔽，因为"数据看起来是有的"。
- 数据库侧它翻译成 `WHERE id < ?`（降序时），走索引 seek，**和页码无关地稳定**。

### 4.4 两种怎么选

| | offset (`skip/take`) | 游标 (`cursor`) |
|---|---|---|
| 能跳页吗 | 能（第 5 页、最后一页） | 不能，只能"下一页/上一页" |
| 深翻性能 | 越翻越慢 | 恒定 |
| 数据插入时 | 页内容会错位（翻页看到重复/漏项） | 稳定 |
| 要 total 吗 | 天然要（配 `count`） | 通常不要，用 `hasMore` |
| 适合 | 后台管理、导出、需要页码的地方 | 信息流、聊天记录、无限滚动 |

**现实里两个都要会，而且经常同时存在**：列表页用 offset（用户要跳页），动态流用游标。别信"游标一定更高级"——不能跳页在后台表里就是硬伤。

`total` 的成本也要知道：`count` 是一次独立的全表/索引扫描，和 `take` 无关。返回 `{ items, total, page, pageSize }` 意味着每次请求两次查询。数据量大时，`hasMore`（多取一条判断）比 `total` 便宜得多。

## 5. 事务：`$transaction`（练习 4）

### 5.1 两种形态，别混

```ts
// 形态 A：数组——一串互不依赖的操作，一起成功或一起失败
await prisma.$transaction([
  prisma.tasks.deleteMany({ where: { userId } }),
  prisma.users.delete({ where: { id: userId } }),
])

// 形态 B：交互式——后面的操作依赖前面的结果
await prisma.$transaction(async (tx) => {
  const user = await tx.users.findUniqueOrThrow({ where: { username } })
  const task = await tx.tasks.create({ data: { userId: user.id, title } })
  return task
})
```

**你已经在用形态 B 了**：`seed.ts` 里整个灌数据流程包在 `$transaction(async (tx) => ...)` 里，因为"先 upsert 用户拿到 id，再建任务"有依赖。上周写对了，这周要能说出为什么是 B 不是 A。

选择标准：**后面的操作要不要用前面的结果**。要 → B；不要 → A（A 更快，且自动串行）。

### 5.2 什么时候必须用

- 多张表的写操作必须同时成立（删用户 + 删他的任务；转账）
- "先查后写"需要原子性（查余额 → 扣款，中间不能被插队）
- 批量操作里任何一条失败都要全部回滚

反过来，**单条 `create` / `update` 本身就是一个事务**，不需要额外包——很多人给每条语句套 `$transaction`，纯属浪费连接。

### 5.3 三个坑

1. **超时**：交互式事务默认 `timeout: 5000ms`、`maxWait: 2000ms`。里面跑循环处理 1000 条数据必然超时，要显式调大，或者改成批量语句。
2. **绝对不要在事务里调外部 IO**（HTTP、LLM 接口、发邮件）。事务开着就是在占连接、持锁，一个 3 秒的 LLM 调用能让整张表的写操作排队。**先算完、再开事务写**，这是第 13 周之后写 LLM 应用时的硬约束。
3. **错误处理**：交互式事务里抛出的任何异常都会回滚，但你要确保异常**真的抛出去了**——`catch` 里忘了 `throw` 是最常见的"以为回滚了其实提交了"。

### 5.4 隔离级别（一句话）

Postgres 默认 Read Committed：**每条语句看到的是语句开始时的已提交数据**。所以同一个事务里查两次，可能看到不同的结果。要"整个事务一个快照"就得 `isolationLevel: 'Serializable'` / `'RepeatableRead'`，代价是冲突重试。本周只要知道有这层、知道默认是什么，写业务时别指望"事务里查了就不会变"。

## 6. N+1：为什么"循环里查"是错的

这是关系查询里最经典的性能问题，本周必须能一句话说清。

```ts
// ❌ N+1：1 次查列表 + N 次查关联
const users = await prisma.users.findMany()
for (const u of users) {
  u.tasks = await prisma.tasks.findMany({ where: { userId: u.id } })
}

// ✅ include：固定条数的查询
const users = await prisma.users.findMany({ include: { tasks: true } })
```

关键认知，别记错：**Prisma 的 `include` 不是 N+1**。一对多关系它发的是**第二条查询**（`SELECT ... FROM tasks WHERE user_id IN (...)`），条数恒定；多对一则可能直接 JOIN 进主查询。所以：

- 关系数据 → 用 `include`，不要循环查
- 只有 id 列表、且关系很远 → 用 `in: ids` 自己拼
- 判断标准：**查询条数是否随数据量增长**。增长就是 N+1。

打开 query log 数一遍查询条数，是最直接的验证方式——练习 1 第 6 题已经让你做了。

## 7. 周六项目产出：我的任务接口（约 3 小时）

**这是本周的核心产出。** 前九周的所有东西在这里汇合：鉴权（第 4 周）、分层（第 6 周）、外键与索引（第 8 周）、Prisma（第 9 周）、关系查询 + 分页 + 事务（本周）。

### 7.1 接口要求

现在的 tasks 路由是 `GET /tasks/list` 靠 body 传参（第 6 周的遗留写法），本周改成 REST：

```text
GET  /tasks/mine?page=1&pageSize=10&completed=false&tag=work
POST /tasks
PATCH /tasks/:id
```

| 要求 | 说明 |
|---|---|
| 鉴权 | 从 `req.user.userName` 拿当前用户（见 `middleware/checkAuth.ts`），**不接受**前端传 username，否则就是越权漏洞 |
| 只返回自己的 | `where: { userId }` 是底线；如果用户不存在，返回 401 而不是空列表 |
| 带标签 | 返回 `tags: string[]`，不要暴露 `taskTags` 中间表结构（用 `select` 压平） |
| 分页 | `page` / `pageSize` 用 zod 校验（`pageSize` 上限 100，别让前端传 100000） |
| 排序 | `createdAt desc, id desc`（第 8 周那条稳定性教训） |
| 响应 | `{ items, total, page, pageSize, hasMore }` |
| 创建 | `POST /tasks` 支持 `tagNames: string[]`，用嵌套写 + `connectOrCreate` |
| 改 | `PATCH /tasks/:id` **只能改自己的**——这是本周的安全考点 |

### 7.2 `PATCH` 的越权陷阱（本周最值钱的一个点）

直觉写法 `prisma.tasks.update({ where: { id } })` 有个洞：任何人拿到别人的任务 id 就能改。

两种正确写法，都要会：

```ts
// 写法 A：extended where unique —— id 是唯一锚点，userId 作为附加条件
const r = await prisma.tasks.updateMany({ where: { id, userId } })
if (r.count === 0) throw new AppError(404, 'TASK_NOT_FOUND', '任务不存在')

// 写法 B：先查归属，再按 id 改（包在事务里才有意义，否则中间可能被改）
```

写法 A 一次往返解决，且天然不泄露"这个 id 存在但不属于你"（统一 404 而不是 403，避免枚举）。第 9 周复盘第 9 题讲的"extended where unique"就是这里用的——`id` 唯一锚点 + 非唯一附加条件。

注意 `updateMany` 返回 `{ count }` 而不是数据，要数据就得再查一次或换写法 B。

### 7.3 步骤（自己排，别照抄顺序）

大致是：schemas（zod）→ repository（四个方法，全部带 `userId`）→ service（映射成大驼峰、BigInt 转字符串、算 `hasMore`）→ controller → routes → 实测。

**层间纪律**：service 里不要出现 `Prisma.xxx` 错误类或 Prisma 的返回类型（第 9 周红灯 3 就是这个）；repository 返回业务类型，错误码翻译在 repository 做。

### 7.4 你会遇到的坑（遇到了回来对）

- **`total` 和 `items` 一致性**：`count` 和 `findMany` 是两次查询，中间数据可能变。要么接受，要么包 `$transaction`（形态 A 就够）。
- **`include` 和分页**：`take` 是限制主表行数的，关联数据不会"少"，别担心。
- **压平 `tags`**：`taskTags: { select: { tag: { select: { name: true } } } }` 出来是 `[{ tag: { name } }]`，要 `.map(x => x.tag.name)`。这个映射放 repository，不要泄到 controller。
- **`completed=false` 的解析**：query string 是字符串 `"false"`，zod 要用 `z.coerce.boolean()` 或 `z.enum(['true','false']).transform(...)`——注意 `z.coerce.boolean()` 会把 `"false"` 转成 `true`，这是个真实的坑，自己验一遍。
- **游标版本**：`GET /tasks/mine?cursor=123` 时不要 `page`，两个参数互斥，用 zod 的 `refine` 约束。
