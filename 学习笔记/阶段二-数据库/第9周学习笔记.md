## 1. 本周全景：为什么需要 ORM

第 7、8 周你手写 SQL 操作数据库，真实项目里在代码中这样拼 SQL：

```ts
// 反面教材：字符串拼 SQL
const rows = await db.query(
  "SELECT * FROM users WHERE username = '" + username + "'"
);
```

三个致命问题：

| 问题 | 后果 |
|---|---|
| 字符串拼接 | SQL 注入（`username` 里塞个 `' OR 1=1 --` 就完了） |
| 返回值是 `any` | 字段名拼错、类型用错，运行时才炸 |
| 表结构改了 | 全靠人肉搜索哪些 SQL 要跟着改，必漏 |

ORM（对象关系映射）的思路：**用代码里的模型定义当"唯一事实源"，SQL 由工具生成**。Prisma 是当前 Node.js 生态最主流的选择，它的工作流正好对应你前两周学的东西：

| 第 7–8 周手写 | 第 9 周 Prisma | 关系 |
|---|---|---|
| `CREATE TABLE users (...)` | `schema.prisma` 里的 `model User` | schema 是建表语句的"源代码" |
| `ALTER TABLE` 改结构 | `prisma migrate dev` 生成迁移文件 | 每次改动有记录、可回滚 |
| `01-create-tables.sql` 手动执行 | 迁移文件按顺序自动应用 | 新环境一键重建 |
| `INSERT INTO` 测试数据 | `prisma/seed.ts` | 用 TS 写，能复用类型 |
| `psql` 里写 SELECT | `prisma.user.findUnique()` | 返回值带完整类型 |

⚠️ 一个重要认知：**ORM 不是替代 SQL，是生成 SQL**。所以第 7、8 周的手写功夫不会白费——看 Prisma 生成的迁移文件、排查慢查询时，你读的还是 SQL。面试问"用过 Prisma 吗"的下一个问题一定是"它生成的 SQL 长什么样"。

## 2. 三步工作流（本周主线，背下来）

```text
写 schema.prisma → prisma migrate dev → 代码里用 Prisma Client
   (想要什么表)      (生成并应用迁移)        (类型安全地查)
```

1. **schema 是唯一事实源**：表结构只在这里定义，不直接进数据库改
2. **migrate 把"变化"变成文件**：每次改 schema，生成一个带时间戳的 SQL 迁移文件，进 git。团队成员拉代码后跑 migrate 就能追上你的表结构
3. **Client 是生成的**：`prisma generate` 读 schema 生成 TS 类型 + 查询 API，改完 schema 类型立刻更新，编译器帮你找出所有受影响的代码

**三条铁律：**

- 表结构变更**永远走 migrate**，不要连数据库手动 ALTER（schema 和实际库会漂移，migrate 直接乱套）
- 已应用的迁移文件**不要手改**（改了就和新环境重放的结果不一致）；要改结构就再生成一个新迁移
- `prisma db push`（跳过迁移文件直接同步）只能在本地原型期用，正式流程禁用

## 3. schema 语法：对照你写过的 SQL

### 3.1 骨架

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"   // 生成 TS Client
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")  // 连接串放 .env，不进 git
}
```

`DATABASE_URL` 格式：`postgresql://用户名:密码@localhost:5432/todo_app`

### 3.2 model 与字段类型对照表

拿第 8 周的 users 表对照着看：

```prisma
model User {
 //┌─字段名(TS+DB)  ┌─TS类型      ┌─DB指令
  id           BigInt   @id @default(autoincrement())  //PRIMARY KEY GENERATED ALWAYS AS IDENTITY
  username     String   @unique @db.VarChar(50) //VARCHAR(50)  UNIQUE  NOT NULL
  email        String   @db.VarChar(100) //VARCHAR(100) NOT NULL  
  passwordHash String   @map("password_hash") @db.VarChar(100)
  createdAt    DateTime @default(now()) @map("created_at")
  updatedAt    DateTime @updatedAt @map("updated_at")

  @@map("users")   // TS 里叫 User，数据库里表名还是 users
}

// @id @unique 管理约束   @db.VarChar(100) 管理类型
```

| SQL（第 8 周） | Prisma schema | 说明 |
|---|---|---|
| `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | `BigInt @id @default(autoincrement())` | 自增主键 |
| `VARCHAR(50) UNIQUE NOT NULL` | `String @unique @db.VarChar(50)` | schema 里字段默认就是 NOT NULL |
| `TIMESTAMPTZ DEFAULT now()` | `DateTime @default(now())` | |
| （手写维护 updated_at） | `@updatedAt` | Prisma 自动在 update 时刷新 |
| 列名 `password_hash` | 字段 `passwordHash` + `@map("password_hash")` | TS 用驼峰，库里保持蛇形 |
| 可空列 `TEXT` | `String?` | 加 `?` 才允许 NULL |

注意两个命名约定：

- **TS 侧一律驼峰**（`passwordHash`），数据库侧保持蛇形（`password_hash`），用 `@map` 桥接
- **model 名用单数大驼峰**（`User`），表名用复数（`users`），用 `@@map` 桥接

### 3.3 枚举（enum）

SQL 里你可能用 `VARCHAR` + CHECK 约束表示状态，Prisma 有真正的枚举：

```prisma
enum TaskStatus {
  PENDING
  IN_PROGRESS
  DONE
}

model Task {
  id     BigInt     @id @default(autoincrement())
  title  String     @db.VarChar(100)
  status TaskStatus @default(PENDING)
  // ...
}
```

TS 里会生成对应的联合类型，写错状态值直接编译报错。

### 3.4 关系字段（第 8 周外键的 Prisma 写法）

一对多（users → tasks），**两边都要写**：

```prisma
model User {
  id    BigInt @id @default(autoincrement())
  // ...
  tasks Task[]                    // 关系字段：一个用户有多个任务（不占数据库列）
}

model Task {
  id     BigInt @id @default(autoincrement())
  title  String @db.VarChar(100)
  userId BigInt @map("user_id")   // 关系标量字段：真实的数据库列（= 第 8 周的 user_id）
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  // ...
}

// completed 就是 SQL 里的 BOOLEAN，直接用 Boolean 即可，不需要 enum
model User {
  id BigInt @id @default(autoincrement())
  username String  @unique @db.VarChar(50)
  email String @db.VarChar(100)
  passwordHash String @map("password_hash") @db.VarChar(100)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at")

  tasks     Task[]     // 反向关系字段：一个用户有多个任务（Prisma 要求两边都声明）
  @@map("users")       // 模型名 User（单数大驼峰），表名还是 users
}

model Tasks {
  id BigInt @id @default(autoincrement())
  userId BigInt  @map("user_id")
  user     User    @relation(fields: [userId], references: [id], onDelete: Cascade)

  title String @db.VarChar(100)
  completed Boolean  @default(false)
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @default(now()) @updatedAt @map("updated_at")

  taskTags  TaskTag[]  // 反向关系字段：一个任务有多个标签关联
  @@map("tasks")
}

model Tag {
  id BigInt @id @default(autoincrement())
  name     String   @unique @db.VarChar(50)

  taskTags TaskTag[]
  @@map("tags")
}

model TaskTag {
  taskId BigInt @map("task_id")
  task   Task @relation(fields: [taskId], references: [id], onDelete: Cascade)

  tagId  BigInt @map("tag_id")
  tag    Tag @relation(fields: [tagId], references: [id], onDelete: Cascade)

  @@id([taskId, tagId])
  @@map("task_tags")
}


```
```sql
 CREATE TABLE users{
   id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
   username VARCHAR(50) UNIQUE NOT NULL ,
   email VARCHAR(100),
   password_hash VARCHAR(100) NOT NULL,
   created_at TIMESTAMPTZ DEFAULT now()
 } 

```
```prisma

model Users {
   id BigInt  @id @default(autoincrement())
   username String  @unique @db.VarChar(50) 
   email String @db.VarChar(100)
   passwordHash @map("password_hash") @db.VarChar(100)
   createdAt DateTime @map("created_at") @db.Timestamptz @default(now())

}

@@map(users)
```


关键理解：

- `userId` 是**标量字段**，对应数据库里真实存在的列（就是你第 8 周手写的 `user_id BIGINT NOT NULL REFERENCES users(id)`）
- `user` / `tasks` 是**关系字段**，不生成数据库列，只是告诉 Prisma"这两张表怎么连"，查询时用 `include` 才能带出关联数据（第 10 周重点）
- `onDelete: Cascade` 就是第 8 周的 `ON DELETE CASCADE`
- 外键列依然默认**没有索引**——第 8 周的教训在 Prisma 里同样成立，要手动加 `@@index([userId])`

多对多（tasks ↔ tags）和第 8 周一样建中间表 `TaskTag`，复合主键写成 `@@id([taskId, tagId])`。本周可以先不做，第 10 周关系查询时再建。

## 4. migrate：把 schema 变化变成迁移文件

### 4.1 核心命令

```bash
# 改完 schema 后：生成迁移 SQL + 应用到数据库 + 重新生成 Client，一步到位
pnpm prisma migrate dev --name init

# 查看迁移状态（哪些已应用、哪些待应用）
pnpm prisma migrate status

# 生产/CI 环境：只应用已有迁移，不生成新的
pnpm prisma migrate deploy
```

`migrate dev --name init` 一次干了三件事：

1. 对比 schema 和数据库现状，生成 `prisma/migrations/<时间戳>_init/migration.sql`
2. 把这个 SQL 应用到数据库
3. 自动跑 `prisma generate` 更新 Client 类型

**打开生成的 migration.sql 读一遍**——你会发现就是你第 8 周手写的那套 `CREATE TABLE`、`REFERENCES`、`ON DELETE CASCADE`。这就是"ORM 生成 SQL"最直接的证据。

### 4.2 迁移文件纪律

- `prisma/migrations/` **必须提交 git**，它是表结构的演进历史
- 新环境重建：clone 代码 → 配好 `DATABASE_URL` → `prisma migrate deploy` → 表结构一模一样
- 改表结构的正确姿势：改 schema → `migrate dev --name add_xxx` → 提交新迁移文件。**永远不手改已提交的迁移**

## 5. Prisma Client：类型安全的查询

### 5.1 单例模式（重要）

```ts
// src/week9/db/prisma.ts
import { PrismaClient } from "@prisma/client";

// 全局单例：整个应用共用一个 Client（内部是连接池）

```

为什么不能每个请求 `new PrismaClient()`？每个实例自带一个连接池，请求一多连接数爆炸，Postgres 直接拒绝连接。这和第 6 周讲的"连接池"是同一个道理。

### 5.3 select：别把密码哈希漏出去

```ts
const user = await prisma.user.findUnique({
  where: { username: "alice" },
  select: { id: true, username: true, nickname: true },  // 只要这几列
  include:{tasks:true} //此处相当于left join，当where不存在时就相当于 inner join
});
//返回的结果是 {id，username，nickname，tasks：[{},]}
// user 的类型里只有这三个字段——想访问 user.passwordHash 直接编译报错

```

默认 `findUnique` 返回**所有列**，包括 `passwordHash`。返回给前端前要么用 `select` 收窄，要么在 service 层显式剔除。这是真实项目里最常见的安全失误之一。

### 5.4 错误码：对照第 8 周的 SQLSTATE

| Prisma 错误码 | 含义 | 对应第 8 周的 |
|---|---|---|
| `P2002` | 唯一约束冲突 | `23505` |
| `P2003` | 外键约束失败 | `23503` |
| `P2025` | 要操作的记录不存在 | （SQL 里没有直接对应，影响行数为 0） |

第 8 周你故意触发过 23503/23505，这周在代码里用 try/catch 接住 `Prisma.PrismaClientKnownRequestError` 再判断 `code`，就是注册接口"用户名已存在"的正确实现方式。

## 6. seed：用 TS 灌测试数据

第 8 周的 `02-insert-data.sql` 用 `TRUNCATE + INSERT` 保证幂等，Prisma 的等价物是 seed 脚本：

```ts
// prisma/seed.ts
import { prisma } from "../src/week9/db/prisma";

async function main() {
  // upsert：存在就更新、不存在就创建 → 天然幂等，反复跑不报错
  const alice = await prisma.user.upsert({
    where: { username: "alice" },
    update: {},
    create: {
      username: "alice",
      email: "alice@example.com",
      passwordHash: "seed_hash_alice",
    },
  });
  // ...
}

main()
  .finally(() => prisma.$disconnect());
```

`package.json` 里注册：

```json
{
  "prisma": {
    "seed": "tsx prisma/seed.ts"
  }
}
```

之后 `pnpm prisma db seed` 手动灌数据；`migrate dev` / `migrate reset` 也会自动触发 seed。

## 9. 复盘问题（周日回答，答不上来的记下来）

> 下面是根据第一轮回答修正后的版本。每题按"机制 + 不这么做会怎样 + 适用场景"组织，面试时照这个深度说。

1. **ORM 解决了哪三个问题？为什么说"ORM 不是替代 SQL，是生成 SQL"？**
   三个问题：字符串拼 SQL 导致注入；查询结果是 `any`，字段/类型错误只能运行时暴露；表结构变更靠人肉搜索 SQL，必漏。
   "生成 SQL"指 schema 是唯一事实源：迁移 SQL 在 migrate 时生成，增删改查 SQL 在运行时由 Client 生成。读迁移文件、看 `EXPLAIN`、排查慢查询时看的仍是 SQL，所以手写 SQL 的功夫没有白费。

2. **Prisma 的三步工作流是什么？每一步的产物是什么文件？**
   `schema.prisma` → `prisma migrate dev` → Prisma Client。
   - schema：`schema.prisma`，表结构的唯一事实源
   - migrate：`prisma/migrations/<时间戳>_<name>/migration.sql`，加上数据库里的 `_prisma_migrations` 执行记录
   - generate（migrate 会自动触发）：生成的 Client 代码和 TS 类型（本项目在 `src/week6/prisma/generated/`）

3. **为什么表结构变更必须走 migrate，不能连数据库手动 ALTER？**
   手动 ALTER 会让 schema 和数据库"漂移"：`migrate dev` 检测到 drift 会要求 reset；新环境重放迁移时得不到手改的结构；没有历史记录，无法审查和回滚；团队成员拉代码后库结构不一致。migrate 把每次变更变成可重放的 SQL 文件，保证任何环境都能从零重建出同一套结构。

4. **`migrate dev` 和 `migrate deploy` 的区别？分别用在什么环境？**
   - `migrate dev`：对比 schema 和数据库，**生成新迁移**并应用，再 generate；会交互提示、可能 reset 丢数据；需要影子库。用于本地开发。
   - `migrate deploy`：**只应用已有迁移**，不生成新迁移，不交互、幂等、可安全重跑，不用影子库，也不触发 seed。用于生产 / CI。
   一句话：dev 是"设计 + 应用"，deploy 是"只应用"。

5. **已应用的迁移文件为什么不能手改？**
   `_prisma_migrations` 表里存了每个迁移的 checksum。改动已应用的迁移会导致 checksum 不匹配，`migrate status` 报 migration modified；其他环境早已按旧版本执行过，历史会分叉。要改结构就新增一个迁移；本地数据可丢时用 `migrate reset` 重放。

6. **schema 里的"关系字段"（`tasks Task[]`）会生成数据库列吗？那它有什么用？**
   不会。关系字段是 Prisma 查询层的虚拟反向关系，不落库；真正的外键列是标量字段 `userId` + `@relation(fields: [userId], references: [id])`。关系字段让 `include`、嵌套写入、`connect` 和类型安全的关系遍历成为可能，Prisma 要求关系两边都声明。

7. **`@map` 和 `@@map` 分别解决什么问题？**
   `@map` 把字段名映射到列名（`passwordHash` → `password_hash`）；`@@map` 把 model 名映射到表名（`Users` → `users`）。它们只改命名，不改类型；改类型用 `@db.VarChar(50)` 这类原生类型标注。

8. **为什么 PrismaClient 要用单例？每个请求 new 一个会怎样？**
   `new` 出来的是多个互相独立的实例，不是单例；每个实例自带一个连接池。每请求 new 一个会让连接数随并发线性增长，Postgres 报 `too many clients already`（53300），还要反复建连接、握手、初始化，延迟和内存都浪费。Client 是连接池的持有者，应该全局共用一个。

9. **`findUnique` 的 `where` 为什么只能放唯一字段？**
   因为它的语义是"最多返回一行"，必须有一个唯一字段作为锚点。纯非唯一条件可能匹配多行，类型层就不允许（现代 Prisma 支持 extended where unique，可以在唯一字段基础上附加非唯一条件，但锚点不能少）。

10. **"用户名已存在"为什么应该用 catch P2002 实现，而不是"先 findUnique 再 create"？**
    先查再插存在竞态：两个并发请求都查到"不存在"，都去 create，第二个撞唯一约束变成 500。catch P2002 把唯一性交给数据库约束，插入是原子的，冲突时稳定返回 409。少一次查询只是顺带的好处，核心是正确性。

11. **seed 用 upsert 保证幂等和 SQL 用 TRUNCATE 保证幂等，思路差别是什么？**
    - TRUNCATE + INSERT 是"声明式重建"：保证库和脚本完全一致，快、可重置自增 ID；但会清空数据，有外键引用时麻烦。适合测试库、可丢弃的 fixture。
    - upsert 是"增量收敛"：保留已有行和 ID，不破坏外键引用；但不会删除脚本里已移除的旧数据，也更慢。适合开发库或不能随便清的库。
    本周 seed 是混合策略：用户/标签有唯一键用 upsert，任务没有唯一业务键所以 delete + create。
