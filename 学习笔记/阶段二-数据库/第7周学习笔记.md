### 1.2 为什么文件/内存存储到头了

第 1–6 周的 `repositories` 用内存数组、JSON 文件存数据，它们和 PostgreSQL 的本质区别：

| 能力 | 内存/文件 | PostgreSQL |
|---|---|---|

## 3. 三分钟概念地图：SQL 世界 = 你熟悉的 TS 世界

你在第 1 周就写过这种 TS 类型：

```ts
interface User {
    id: number
    username: string
    passwordHash: string
    createdAt: Date
}
```

SQL 里的对应物：

| SQL 概念 | 类比 | 说明 |
|---|---|---|
| database | 一个独立项目 | 一个库给一个应用用，别全塞一起 |
| table（表） | `User[]` 数组 | 一张表存一类对象 |
| row（行） | 数组里的一个对象 | 一条记录 |
| column（列） | 对象的字段 | 列的类型 = TS 类型 |
| constraint（约束） | TS 类型检查 | 数据库替你拦非法数据 |

常用列类型（先记这 6 个就够）——总览表先背下来，后面逐个上手：

| SQL 类型 | 类比 TS | 用在哪 |
|---|---|---|
| `BIGINT` | `number`（整数） | `id`、计数 |
| `TEXT` / `VARCHAR(n)` | `string` | 长文本用 TEXT；定长/限长用 VARCHAR(n) |
| `BOOLEAN` | `boolean` | `completed` |
| `TIMESTAMPTZ` | `Date` | `created_at`——**永远用带时区的** |
| `NUMERIC` | number（要精确） | 金额，别用浮点 |
| `JSONB` | `object` | 第 11 周存聊天记录用 |

**① BIGINT——整数（id 专用）**

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY   -- 建表：id 自动生成，不用手填
SELECT count(*) FROM users;                          -- 计数返回的也是 BIGINT
SELECT * FROM users WHERE id = 1;                    -- 取：按 id 定位
```

- 64 位整数，范围 ±9.2×10¹⁸，计数、id 根本用不完
- ⚠️ 坑（先埋个钩子，第 9 周 Prisma 接入会撞上）：JS 的 `number` 只能精确表示到 2⁵³（约 9 千万亿），超过会丢精度。到时 Prisma 会把 bigint 自动当字符串处理，现在有印象即可

**② TEXT / VARCHAR(n)——文本**

```sql
username      VARCHAR(50)   -- 限 50 个字符
password_hash TEXT          -- 不限长（哈希固定 60 字符也用 TEXT，语义是"可能很长"）
title         TEXT NOT NULL
```

- `VARCHAR(n)` 限长，超长报：`value too long for type character varying(50)`；`TEXT` 不限长
- 长度按**字符**算不是字节：中文"数据库"算 3 个字符，VARCHAR(50) 放心存中文
- ⚠️ 不会自动去空格：存 `' alice '` 就是带头尾空格的值，`WHERE username = 'alice'` 会查不到（第 8 周有个去空格练习，先记住这个坑）

**③ BOOLEAN——布尔**

```sql
completed BOOLEAN NOT NULL DEFAULT FALSE
```

- 取值只有 `TRUE` / `FALSE` / `NULL`（别忘了还能 NULL）
- 插入时也认 `'t'/'f'/'yes'/'no'/'1'/'0'` 这些宽松写法，但存进去统一是 t/f
- 查询：`WHERE completed` 或 `WHERE completed = TRUE`；**判断空必须写 `IS NULL`，不能写 `= NULL`**（NULL 不等于任何值，练习 5 会踩）
- 对应 TS 的 `boolean`，后端返回 JSON 就是 `true / false`

**④ TIMESTAMPTZ——带时区时间（时间列唯一选择）**

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT now()   -- 插入不用管，自动打当前时间
SELECT * FROM tasks WHERE created_at BETWEEN '2026-09-01' AND '2026-09-30';
```

- 存：内部统一按 UTC；取：按你的会话时区显示——同一时刻，任何时区的人看到的都是"对的"
- ⚠️ 千万别用 `TIMESTAMP`（不带时区）：它只是"墙上时间"，没有时区含义，跨时区看同一列会错位 8 小时。生产事故级误区，记住：**时间列一律 timestamptz**
- 对应 TS 的 `Date`

**⑤ NUMERIC——精确小数（金额专用）**

```sql
price NUMERIC(10, 2)   -- 总共最多 10 位数字，其中 2 位小数
```

- 精确十进制：`0.1 + 0.2 = 0.3`，不会出现 JS 浮点那种 `0.30000000000000004`
- ⚠️ 别用 `DOUBLE PRECISION` / `REAL`（浮点）存金额——第 1 周学过的 0.1+0.2 问题，数据库浮点同样有
- ⚠️ 坑（第 9 周撞上）：Node 的 pg 驱动默认把 numeric 当**字符串**返回（防 JS 丢精度），接口层可能拿到 `"19.99"`，要转换或交给 Prisma 处理
- 代价：比浮点慢、占空间。只用在要精确的场景（金额、评分），普通计数用 BIGINT

**⑥ JSONB——任意结构（第 11 周主角，先认识）**

```sql
messages JSONB   -- 聊天记录：形状随便的 JSON 整块塞进去
SELECT data->>'name' FROM t;                    -- ->> 取出字段（字符串）
WHERE data @> '{"role": "user"}';              -- 包含查询，能配合索引
```

- JSON 的"二进制版"：存进去会解析、排序 key、支持索引，查询比普通 JSON 类型快
- ⚠️ 别拿它当万能存储：需要"查单个字段 / 做关联"的数据应该建独立列；JSONB 只装"整块存取、不参与复杂查询"的数据（聊天记录正合适）

> 一句话：**表 = 类型 + 数组，行 = 对象，SQL = 对数组做 filter/sort/paginate 的语法**。选类型 = 想清楚"这列装什么、要不要计算"：是整数还是文本？要不要精确（金额）？要不要参与 WHERE 过滤？拿不准就按这个问自己，第 8 周建 tags 表还会再复习一遍。

### 5.1 CREATE TABLE 语法骨架

```sql
CREATE TABLE 表名 (
    列名 类型 约束,
    列名 类型 约束,
    ...
);
```

### 5.2 五类约束（背下来，面试/排错都靠它）

约束 = 数据库版的 TS 类型检查，但它不拦"编译"而拦"写入"：**任何违反约束的 INSERT / UPDATE 会整条失败并回滚**，不会"跳过那条"。所以后端少写一堆 if，约束在数据库层兜底。

快速总览（背下来，面试/排错都靠它）：

| 约束 | 作用一句话 | 违反时报什么 | SQLSTATE |
|---|---|---|---|
| `PRIMARY KEY` | 唯一 + 非空，一条记录的身份证 | 撞主键报的是 `duplicate key value ... violates unique constraint`（主键底层就是唯一索引） | `23505` |
| `NOT NULL` | 不允许为空 | `null value in column "xxx" violates not-null constraint` | `23502` |
| `UNIQUE` | 值不能重复（**但多个 NULL 允许**） | `duplicate key value ... violates unique constraint "xxx_key"` | `23505` |
| `FOREIGN KEY` | 引用另一张表的主键，防"孤儿数据" | `insert or update on table "tasks" violates foreign key constraint "tasks_user_id_fkey"` | `23503` |
| `CHECK` | 自定义规则（范围/枚举） | `new row for relation "xxx" violates check constraint "xxx_check"` | `23514` |
| `DEFAULT` | 不填时自动填 | 不报错，自动补 | — |

> 认错技巧：报错原文里 `constraint "xxx"` 后的名字就是约束名，且报错自带表名、列名。以后看后端日志，先抓 **SQLSTATE + constraint 名**，立刻知道是哪个库哪张表哪个约束拦的。

逐个说人话 + 声明写法（练习 2 要亲手违反一遍，对照这里）：

**① PRIMARY KEY（主键）**

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY   -- 列级：单列主键最常见
-- 复合主键要写表级（了解即可）：PRIMARY KEY (user_id, task_id)
```

- 本质 = UNIQUE + NOT NULL 合体，一张表**最多一个主键**
- PG 会自动给主键建唯一索引 → 用 `WHERE id = 1` 定位行最快最准
- 撞主键和撞 UNIQUE 报的错**完全一样**（都是 23505），别奇怪——底层机制相同

**② NOT NULL（不能为空）**

```sql
password_hash TEXT NOT NULL
```

- 违反 → `23502`，该填的字段没填，插入/更新整条失败
- ⚠️ 误区：**空字符串 `''` ≠ NULL**。`''` 是"填了但内容为空"，NULL 是"压根没填"，`''` 能顺利通过 NOT NULL
- 实战：业务必填字段（用户名、标题、密码哈希）都加 NOT NULL，让数据库兜底，别只靠后端 if

**③ UNIQUE（不能重复）**

```sql
email VARCHAR(255) UNIQUE
```

- 违反 → `23505`，后端通常翻译成 HTTP 409（资源冲突）
- **关键特性：多个 NULL 不冲突**。三个用户都没填邮箱 → 三个 NULL，不报错。语义正好 = "邮箱可以没有，但有了就不能和别人一样"（5.4 的 users 表就是这个场景）
- 想让两列"合起来不重复"（如同一用户的同一种标签），要写表级：`UNIQUE (user_id, tag)`

**④ FOREIGN KEY（外键）**

```sql
user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE   -- 列级
-- 表级写法（多列外键时才需要）：FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
```

- 作用：数据库保证 `user_id` 一定指向真实存在的用户 → **从根上杜绝孤儿数据**（你 week2 靠代码手写的检查，它接管了）
- 违反 → `23503`，报错会带 `DETAIL: Key (user_id)=(999) is not present in table "users"`
- `ON DELETE` 三选一，被引用行被删时怎么处理引用它的行：

  | 行为 | 用户被删时他的任务 | 适用场景 |
  |---|---|---|
  | `CASCADE` | 任务跟着一起删 | 任务离开用户没意义（本周 tasks 用它） |
  | `SET NULL` | 任务的 `user_id` 变成 NULL | 想保留记录，但外键列要允许 NULL |
  | `RESTRICT`（不写时的默认） | 直接报错，拒绝删用户 | 订单/日志这类绝不能丢的 |

- 限制：被引用的列必须是 PRIMARY KEY 或 UNIQUE

**⑤ CHECK（自定义规则，顺带认识）**

```sql
rating INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5)
status  TEXT NOT NULL CHECK (status IN ('pending', 'done'))
```

- 专门拦"值域"问题：必须非负、只能在 1~5、只能在这几个枚举值里
- 违反 → `23514`。本周看懂这一个例子就够，第 8 周加索引时一起深入

**⑥ DEFAULT（默认值，严格说不是约束）**

```sql
completed BOOLEAN NOT NULL DEFAULT FALSE
created_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

- 不拦数据，只是**缺省值**：INSERT 没写这列 → 自动填上
- ⚠️ 陷阱：DEFAULT 只在**这列压根没出现在 INSERT 里**时生效；你显式写 `NULL` 进去照样违反 NOT NULL，它不会帮你兜。练习 4 有机会踩到，先记住

一句话串联自测：

> "必须有的"加 `NOT NULL` → "不能重复的"加 `UNIQUE` → "要被别人引用的"设 `PRIMARY KEY` → "引用别人的"加 `FOREIGN KEY` → "有取值范围的"加 `CHECK` → "自动打点的"用 `DEFAULT`。

顺带一提：练习 2 第 3 步可以再补一条——插一条 `rating = 99` 触发 CHECK，把 `23514` 也抄进笔记。

### 5.3 生产级命名规范（从这周开始养成）

- 表名：复数、全小写、下划线分隔（`users`、`tasks`、`task_tags`）
- 列名：全小写蛇形（`password_hash`，不是 `passwordHash`）
- 主键统一叫 `id`
- 时间列统一 `created_at` / `updated_at`，类型一律 `TIMESTAMPTZ`
- 外键列 = 被引用表名单数 + `_id`：`tasks.user_id` 引用 `users.id`

> 为什么坚持这套约定？因为以后 Prisma model 直接映射表，命名混乱会让 schema 没法看；而且第 6 周学的"一致性"原则在这里同样适用。

### 5.4 第 6 周的 users 表，SQL 版

你 week2 的注册登录用户，在数据库里长这样：

```sql
CREATE TABLE IF NOT EXISTS users (
    id            BIGINT        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username      VARCHAR(50)   NOT NULL UNIQUE,
    email         VARCHAR(255)  UNIQUE,
    password_hash TEXT          NOT NULL,
    created_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ   NOT NULL DEFAULT now()
);
```

注意三件事：

1. **`BIGINT GENERATED ALWAYS AS IDENTITY`** 是标准写法：主键自动生成、不回退，比老语法 `SERIAL` 更现代（PG 10+ 用 IDENTITY）
2. `email` 允许 NULL，但 UNIQUE——PostgreSQL 允许**多个 NULL**，所以"三个用户都没填邮箱"不冲突，这正符合真实业务
3. `created_at` 用 `DEFAULT now()`：插入时不填自动打时间戳，类型是带时区的 `TIMESTAMPTZ`

再建第 6 周待办对应的表（第 8 周才正式学 JOIN，这里先把外键立起来）：

```sql
CREATE TABLE IF NOT EXISTS tasks (
    id         BIGINT        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    BIGINT        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title      TEXT          NOT NULL,
    completed  BOOLEAN       NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ   NOT NULL DEFAULT now()
```

### 8.1 SELECT 的结构 = 挑列 + 过滤行 + 排序 + 限量

```sql
SELECT 列1, 列2            -- 要哪几列（别没事就 *）
FROM 表
WHERE 条件                 -- 要哪些行
ORDER BY 列 ASC|DESC       -- 排序
LIMIT 数量 OFFSET 跳过几行; -- 分页
```

### 8.3 排序 + 分页（本周重点）

查 alice 未完成的最近任务：

```sql
SELECT id, title, completed, created_at
FROM tasks
WHERE user_id = (SELECT id FROM users WHERE username = 'alice')
  AND completed = FALSE
ORDER BY created_at DESC, id DESC
LIMIT 10 OFFSET 0;
```

分页公式（对应你 week2 接口里的 `page` / `pageSize`）：

```text
OFFSET = (page - 1) * pageSize
第 1 页(page=1, pageSize=10) → LIMIT 10 OFFSET 0
第 2 页(page=2, pageSize=10) → LIMIT 10 OFFSET 10
```

查总数拿总页数：

```sql
SELECT count(*) FROM tasks WHERE user_id = 1;
```

> 提前埋个钩子：`LIMIT/OFFSET` 在数据量大以后会越来越慢（每翻一页都要从头数），第 10 周会学"游标分页"。本周先把 OFFSET 公式用熟。

## 11. 本周复盘问题（周日回答，答不上来的记下来下周补）

- 为什么第 7 周先学裸 SQL，而不是直接上 Prisma？
  先懂数据库自己在干嘛，再用 Prisma 偷懒。直接上 Prisma 时，报错只会看到一坨英文异常，不知道它背后跑了哪条 SQL、为什么失败；先能自己写 SQL，Prisma 就只是"自动生成 SQL 的工具"，不是黑盒。SQL 还是通用技能（Prisma / pgAdmin / 换库都用它）。
- 内存数组/JSON 文件和 PostgreSQL 的本质差别是什么？repositories 层以后会变成什么样？
  内存/文件：重启内存丢、文件脏，多请求会互相覆盖，查询靠手写 filter/sort，完整性靠代码自觉；PostgreSQL：持久化、并发控制、约束兜底、百万级数据也扛得住。repositories 层不会消失，只是里面从"操作数组/文件"换成"执行 SQL"。
- `GENERATED ALWAYS AS IDENTITY` 和 `SERIAL` 有什么区别？为什么选前者？
  两者都自增，区别在于：① `SERIAL` 是老方言/语法糖（integer 列 + sequence + DEFAULT nextval），允许手动往 id 插值，容易把序列搞乱；② `IDENTITY` 是 SQL 标准（PG 10+），序列归列所有（删列即删序列），`GENERATED ALWAYS` 下显式插 id 会直接报错（除非 `OVERRIDING SYSTEM VALUE`）——更安全、语义更清晰，所以选它。

- UNIQUE 约束遇到多个 NULL 会怎样？这在 `email` 可空场景下意味着什么？
  PG 里 NULL 互不相等，所以 UNIQUE 列可以有多个 NULL，不冲突。email 可空场景下这正是想要的行为：邮箱可以不填（很多人空着不冲突），填了就必须唯一。不要加 NOT NULL——加了反而强制人人都有邮箱，违背"邮箱可选"的业务（见 5.4 的 users 表）。
- `ON DELETE CASCADE` 和 `RESTRICT` 分别适合什么场景？
  ① `CASCADE`：删父行时跟着删子行，适合"子数据离开父就没意义"（tasks 属于 user，user 删了任务一起删）；② `RESTRICT`：父行还被引用时禁止删、直接报错，适合"绝不能丢的子数据"（订单引用商品，商品不能因为有订单就被删）；③ `SET NULL`：保留子记录、外键置空，适合"想留记录但外键可空"。
- `UPDATE` / `DELETE` 为什么必须带 WHERE？`RETURNING` 解决了什么后端痛点？
  `UPDATE`/`DELETE` 不带 WHERE 会作用于整张表（改/删所有行），生产里属事故级操作，所以必须带 WHERE、尽量按主键定位。`RETURNING` 在**同一条语句内**返回被影响的行（INSERT/UPDATE/DELETE 都能用），痛点是：① 省掉第二条 SELECT，少一次往返；② 避免"写完到再读之间"被别的请求改掉的竞态；③ INSERT 时能拿回数据库生成的 id / created_at。

- `LIMIT/OFFSET` 分页的公式是什么？它有什么隐患（提示：数据量大以后）？

limit pageSize OFFSET (pageNum-1)*pageSize
  隐患：OFFSET 越大越慢——数据库要先把前面 `(pageNum-1)*pageSize` 行全扫描并丢弃再取本页，翻深页白扫（第 10 周学的"游标/keyset 分页"来解决）。另外 ORDER BY 不安定时会漏行/重行，要带 `id` 兜底。
- `TIMESTAMPTZ` 和 `TIMESTAMP` 差在哪？为什么时间列统一用带时区的？
  `TIMESTAMP`（不带时区）只存"墙上时间"，跨时区看同一列会差 8 小时（事故级）；`TIMESTAMPTZ` 内部统一按 UTC 存、按会话时区显示，任何时区看到的都是同一时刻。所以时间列一律用 `timestamptz`。
- 数据库密码和连接串应该放哪？违反会怎样（复习第 6 周 config 的教训）？
  放环境变量（`.env`，并加进 `.gitignore`），由 config 模块集中读取+校验（第 6 周教训），代码里绝不硬编码。违反后果：连接串/密码提交进 git 就泄露（删文件也还在历史里），换环境还得改代码。
- 如果让你给第 6 周 `repositories` 的 `findAll` 写"未来 SQL 版"，长什么样？
  `RETURNING` 只能用于 INSERT/UPDATE/DELETE，**不能用于 SELECT**；`findAll` 的 SQL 版是普通 SELECT：
  ```sql
  SELECT id, user_id, title, completed, created_at, updated_at
  FROM tasks
  WHERE user_id = $1              -- 可选过滤（对应 findAll 的条件）
  ORDER BY created_at DESC, id DESC
  LIMIT $2 OFFSET $3;             -- 可选分页
  ```
  要点：① 用 `SELECT ... FROM`，不要 `RETURNING`；② 别 `SELECT *`，把列出来（见 8.1）；③ 带 `ORDER BY` 保证顺序稳定；④ Node 里用占位符 `$1`，不拼字符串（见 8.4）。
